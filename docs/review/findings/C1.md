### C1-01 Auth access + long-lived refresh tokens stored in plaintext SharedPreferences (not secure storage on mobile)
- severity: High
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/providers/auth_provider.dart:84-86 (write), :145-147 (clear)
- evidence: |
    final prefs = await SharedPreferences.getInstance();
    await prefs.setString('jwt_token', access);
    await prefs.setString('refresh_token', refresh);
    ...
    await prefs.remove('jwt_token');
    await prefs.remove('refresh_token');
- impact: |
    The opaque refresh token is long-lived (it is the credential that mints new
    access JWTs for the whole session). On Android native it lands in the app's
    plaintext `shared_prefs/*.xml`; on iOS in `NSUserDefaults` plist — neither is
    Keychain/Keystore, so it is recoverable from a device backup, a rooted/jailbroken
    device, or ADB `run-as`. This is inconsistent with the repo's own crypto-key
    handling, which uses `flutter_secure_storage` (Keychain on iOS, Keystore on
    Android) via `DualStorage` (frontend/CLAUDE.md §"DualStorage"; pubspec
    `flutter_secure_storage: ^9.2.4`). On the web/PWA target the token sits in
    `localStorage`, exfiltratable by any same-origin XSS (link-preview / rendered
    message content is an injection surface elsewhere in the app). No documented
    accepted-limit covers auth-token storage (CLAUDE.md only documents key storage).
- fix: |
    Route token persistence through the existing `DualStorage`/`FlutterSecureStorage`
    pattern used by `encryption/signal_stores.dart` so mobile gets Keychain/Keystore;
    keep the web `localStorage` path (the documented durability trade-off) but scope it
    behind `kIsWeb` exactly as `DualStorage` already does. Minimum: store the
    long-lived refresh token in secure storage on `!kIsWeb`.

### C1-03 No request timeouts on any auth/REST/media HTTP call
- severity: Medium
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/services/api_service.dart:38-42 (login), :58-62 (refresh), :380 (fetchMediaBytes), :388-391 (fetchMe) — pattern repeats for every method
- evidence: |
    final response = await _httpClient.post(
      Uri.parse('$baseUrl/auth/login'),
      headers: {'Content-Type': 'application/json'},
      body: jsonEncode({'identifier': identifier, 'password': password}),
    );   // no .timeout(...)
- impact: |
    `http.Client` has no default timeout. On a half-open TCP connection (common on
    mobile network handoff, captive portals, or a backgrounded iOS PWA resuming), the
    awaited future never completes: the login spinner (`_loading`, auth_form.dart:42)
    hangs forever with no error, and `ensureSessionReady()` invoked on resume / by the
    15-min timer (auth_provider.dart:153, :185) can wedge silently. `refreshSession`
    maps HTTP 408 to a transient error but that only helps when the *server* answers.
- fix: |
    Wrap calls in `.timeout(const Duration(seconds: N))` (or pass a timeout-configured
    client) and translate `TimeoutException` into `SessionRefreshTransientException`
    for the refresh path so the existing retry/keep-session logic
    (auth_provider.dart:99-118) engages instead of hanging.

### C1-04 AppConfig.baseUrl falls back to insecure http://host:3000; no prod Android-native BASE_URL wiring
- severity: Medium
- confidence: High
- dimension: BUILD/RELEASE
- location: frontend/lib/config/app_config.dart:13-20
- evidence: |
    static String get baseUrl {
      if (_envUrl.isNotEmpty) return _envUrl;
      // Auto-detect: use the same host as the browser URL, port 3000
      final host = Uri.base.host;
      return 'http://$host:3000';
    }
- impact: |
    Correct production web is saved only by `deploy-web.ps1` passing
    `--dart-define=BASE_URL=https://fireplace.ignorelist.com` (verified in deploy-web.ps1:70).
    If any build omits BASE_URL the app silently targets PLAINTEXT `http://<host>:3000`:
    on the https iOS PWA every request becomes mixed-content-blocked (app fully dead),
    and on a misconfigured build Bearer tokens would traverse cleartext. For the upcoming
    Android native target there is NO committed release build that sets BASE_URL — only
    dev scripts (`run_android_on_x.ps1:30` → `http://10.0.2.2:3000`), so a release APK
    built without the define resolves `Uri.base.host` to a non-routable host over http.
- fix: |
    Add a compile-time guard (assert/throw when `_envUrl.isEmpty` in release/
    `!kDebugMode`), default the fallback scheme to `https`, and add an Android release
    build wrapper that injects `--dart-define=BASE_URL=https://fireplace.ignorelist.com`
    mirroring `deploy-web.ps1`.

### C1-07 Cold-start flash of login screen — token load is fire-and-forget with no loading/splash gate
- severity: Low
- confidence: Medium
- dimension: UX READINESS
- location: frontend/lib/providers/auth_provider.dart:18 (`_loadSavedToken()` in ctor, not awaited) ; frontend/lib/main.dart:116-137 (AuthGate)
- evidence: |

    // main.dart AuthGate:

- impact: |
    `isLoggedIn` is false until `_loadSavedToken` reads SharedPreferences and restores

### C1-08 login() persists tokens before fetchMe; a fetchMe failure leaves a half-authenticated state
- severity: Low
- confidence: Medium
- dimension: CORRECTNESS & STATE

- evidence: |

    await _persistTokens(body);            // tokens written to prefs + memory here

- impact: |

### C1-09 H-04 media host-gate is correctly origin-scoped (positive); token-attach uses a substring check
- severity: Info
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/services/api_service.dart:355-385 ; rewriteLoopbackMediaUrl :411-438
- evidence: |
    final sameOrigin = resolvedUri != null && baseUri != null &&
        resolvedUri.scheme == baseUri.scheme &&
        resolvedUri.host == baseUri.host &&
        resolvedUri.port == baseUri.port;
    final isLegacyCloudinary = resolvedUri != null &&
        resolvedUri.scheme == 'https' && resolvedUri.host == 'res.cloudinary.com';
    if (!sameOrigin && !isLegacyCloudinary) { throw Exception('Refusing to fetch media from untrusted host...'); }
    final headers = sameOrigin && resolved.contains('/media/msgs/')
        ? {'Authorization': 'Bearer $token'} : <String, String>{};
- impact: |
    Confirmed: the sender-controlled `mediaUrl` is gated by full ORIGIN (scheme+host+port),
    NOT a path substring, so an attacker-chosen host is rejected and the Bearer token can
    never be sent cross-origin — H-04 holds. Minor: the token-attach gate uses
    `resolved.contains('/media/msgs/')` (substring incl. query) rather than a path-prefix
    check, but since it only fires when `sameOrigin` is already true, the token never
    leaves the backend origin — benign. `rewriteLoopbackMediaUrl` only rewrites
    `localhost`/`127.0.0.1` to baseUrl's authority, which can only make a URL same-origin
    with the trusted backend, not bypass the gate.
- fix: |
    No action required. Optional hardening: switch the token-attach condition to a path
    check (`resolvedUri.path.startsWith('/media/msgs/')`) for clarity.
