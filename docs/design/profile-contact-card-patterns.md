# Profile/contact card patterns — source research for Fireplace (2026-07-13)

**Purpose.** Concise, first-party evidence for a future Fireplace user card. This is research, not a feature specification. Facts are source-cited; the final section contains **recommendations**, not claims about existing apps.

## What the established products actually support

### 1. Hero, identity, and media

- **Telegram has an intentionally media-led profile surface.** Its official Android client contains an `AvatarsViewPager`, a pager indicator, a full-avatar list, and code that translates/scales the avatar and name during the profile transition; Telegram's API also exposes a full user-photo list. This is direct source evidence for an expanded, gallery-capable hero that can compact rather than a documented contract for a particular scroll curve. [Android source](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/ProfileActivity.java) · [photo-list API](https://core.telegram.org/method/photos.getUserPhotos)
- Telegram's official product post says redesigned profiles provide immediate shared-media access and browsing of profile pictures; its viewer advances profile/chat media by tapping the image's left or right side. [Telegram blog](https://telegram.org/blog/new-profiles-people-nearby)
- Telegram supports a profile **video**, lets its owner select the static chat-photo frame, and lets them restore a prior profile photo or video as the main one. [Telegram blog](https://telegram.org/blog/profile-videos-people-nearby-and-more)
- **Signal deliberately documents the smaller model:** an encrypted profile is a name and picture; first name is required, while last name and photo are optional. Signal's support material establishes a single-photo editor (camera or photo library), not an avatar-history gallery. [Signal Profiles](https://support.signal.org/hc/en-us/articles/360007459591-Signal-Profiles-and-Message-Requests) · [Edit Profile](https://support.signal.org/hc/en-us/articles/360007059952-Edit-my-Profile)
- **Discord demonstrates the identity-surface alternative:** an avatar may be selected from a Recent Avatars collection; its profile can additionally carry an About Me area and an image/GIF banner, with profile colors and effects. [Discord Custom Profiles](https://support.discord.com/hc/en-us/articles/4403147417623-Custom-Profiles)

### 2. Names, handles, and the addressability boundary

- Telegram's public username is discoverable in global search, permits messages from people who do not know the phone number, and has a shareable `t.me/username` link that opens a chat. Telegram explicitly warns users not to set one if they are uncomfortable with that reachability. [Telegram FAQ — username](https://telegram.org/faq#q-what-are-usernames-how-do-i-get-one) · [Telegram FAQ — `t.me`](https://telegram.org/faq#q-how-does-t-me-work)
- Signal separates a profile name from a username: the username is optional and only initiates contact without sharing a phone number; it is not the profile name. Signal lets owners share it by an exact username, QR code, or opaque URL; once a request is accepted, the chat presents the profile name/image rather than the username. [Signal usernames](https://support.signal.org/hc/en-us/articles/6712070553754-Phone-Number-Privacy-and-Usernames)
- Discord likewise separates the prominent display name from the unique username, describing the latter primarily as an identifier for friend requests and identity validation. [Discord usernames and display names](https://support.discord.com/hc/en-us/articles/12620128861463-New-Usernames-Display-Names)

### 3. Actions belong with the relationship, not only with the profile

- Signal's message-request surface offers **Block**, **Delete**, and **Accept**; accepting permits messaging/calling and profile visibility. Its regular chat header is also an entry point for blocking. [Signal Profiles and Message Requests](https://support.signal.org/hc/en-us/articles/360007459591-Signal-Profiles-and-Message-Requests) · [Signal blocking](https://support.signal.org/hc/en-us/articles/360007060072-Block-numbers-usernames-or-groups)
- Telegram's profile model exposes relationship/capability state such as blocked, available phone/video calls, common-chat count, and peer settings, rather than treating a profile as merely static biography. [Telegram profile API](https://core.telegram.org/api/profile)
- WhatsApp says its privacy controls let people choose what they share, how they appear online, and who can contact them; Chat Lock hides locked chats from the main list in a Locked Chats folder. [WhatsApp Privacy](https://www.whatsapp.com/privacy)

### 4. Notifications are first-class, local-to-the-conversation controls

- Telegram places mute controls in the chat header/info path and distinguishes **Disable Sound** (silent delivery) from **Mute** (notifications off); it supports a specified mute duration. [Telegram notification controls](https://telegram.org/blog/notifications-bots)
- Signal reaches per-chat notification settings through the contact/chat header. It supports a duration-based mute, shows a mute icon on the header/name afterward, offers per-contact custom message/call sounds, and offers notification-text privacy choices including no name or message. [Signal notification options](https://support.signal.org/hc/en-us/articles/360043273491-In-App-Notification-Options)
- Discord supplies an escalation ladder: server-wide mute with duration, individual-channel overrides, and `All` / `Mentions` / `Nothing` / `Mute` choices; its documented `Mute` override silences even mentions. [Discord notification settings](https://support.discord.com/hc/en-us/articles/215253258-Notifications-Settings-101)
- WhatsApp maintains a first-party help article specifically for muting/unmuting individual or group chat notifications. This note makes no claim about its current durations because the dynamically rendered article body was not inspectable in this pass. [WhatsApp Help](https://faq.whatsapp.com/694350718331007/)

### 5. Motion and accessibility constraints

- Telegram's official source is evidence of profile-avatar transform animation and a pager, but its public documentation does **not** specify a canonical collapse threshold, duration, easing, haptics, or a reduce-motion variant. Do not present an inferred imitation as Telegram parity. [Telegram Android profile source](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/ProfileActivity.java)
- Apple advises minimizing or eliminating animation when Reduce Motion is enabled, and avoiding motion in frequent interactions. [Apple HIG — Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- WCAG 2.2 SC 2.2.2 requires a pause, stop, or hide mechanism for automatically moving content lasting more than five seconds alongside other content, unless essential; this includes an explicit distraction/accessibility rationale. [W3C — Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

## Design implications and risks — analysis, not product facts

- **Gallery is not a harmless avatar upgrade.** [INFERENCE] A profile-video/previous-photo model turns the card into a media viewer and creates retention, consent, bandwidth, and preview-motion decisions. Signal's documented single optional picture is a privacy-preserving counter-pattern. [Telegram profile media](https://telegram.org/blog/profile-videos-people-nearby-and-more) · [Signal profile model](https://support.signal.org/hc/en-us/articles/360007459591-Signal-Profiles-and-Message-Requests)
- **A public handle is a contact-discovery and spam policy.** [INFERENCE] Telegram's own warning ties public username search directly to unsolicited messages; Signal's exact, optional, non-directory handle is the privacy-oriented counter-pattern. [Telegram FAQ](https://telegram.org/faq#q-what-are-usernames-how-do-i-get-one) · [Signal usernames](https://support.signal.org/hc/en-us/articles/6712070553754-Phone-Number-Privacy-and-Usernames)
- **Mute must be visibly stateful and scoped.** [INFERENCE] Signal displays its mute state at the header, while Telegram and Discord show that silent, timed mute, mention-only, and hard mute are different promises. A generic bell without scope or expiry is ambiguous. [Signal](https://support.signal.org/hc/en-us/articles/360043273491-In-App-Notification-Options) · [Telegram](https://telegram.org/blog/notifications-bots) · [Discord](https://support.discord.com/hc/en-us/articles/215253258-Notifications-Settings-101)
- **Decorative profile theming can defeat legibility.** [INFERENCE] Discord's banner/color/effect model demonstrates expressive identity, but it also expands contrast, busy-background, animation, and motion-preference responsibilities. [Discord Custom Profiles](https://support.discord.com/hc/en-us/articles/4403147417623-Custom-Profiles) · [Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

## Deliberate non-claims

This research did not establish a first-party Signal collapsing hero or avatar gallery, nor a precise Telegram collapse curve/duration/haptic contract. Those details require product design and prototype testing, not cargo-cult implementation.

## Recommendations for Fireplace — not sourced facts

1. **Start with a two-state card, not a clone.** Default to a compact, stable app bar (small avatar, display name, status/mute state); expand only after an explicit tap or deliberate drag to a hero with a larger avatar, name, optional handle, and relationship actions. Let normal upward scroll compact the hero, but keep the title/Back control stable. This captures the useful Telegram hierarchy without claiming undocumented timing parity.
2. **Use a relationship-aware action strip.** Put primary safe actions first: `Message`, `Mute`, and a contextual overflow. Show `Accept`/`Block`/`Delete request` only for an inbound request; place destructive `Block` behind an explicit confirmation. Do not render unavailable capabilities as disabled chrome.
3. **Make notifications an immediate, reversible card section.** Show an unambiguous current state (`On`, `Silent`, `Muted until …`, `Muted`) beside a bell; make duration selection local to the conversation and persist it per viewer/conversation, never as a public profile attribute. Add mention-only only if Fireplace later has mentions worth honoring.
4. **Keep v1 media and theming boring.** One static avatar, app-owned background, and app-theme-derived surfaces are the right baseline. Defer profile banners, user-selected profile backgrounds, animated effects, profile video, and avatar history until their storage/retention, upload limits, privacy visibility, first-frame, and low-bandwidth behavior have product decisions. If a gallery ships later, make it explicit (`Photos`, count, pager dots, close control), never surprise autoplay.
5. **Separate human-readable identity from addressability.** Present display name first; render an optional immutable-looking handle second with copy/share behavior. Before making handles globally searchable, choose deliberately between Telegram-style public discovery and Signal-style exact-link/QR initiation; do not accidentally create a directory through a search field.
6. **Treat reduced motion and accessibility as release requirements.** Reduced motion should snap/crossfade the hero and freeze decorative media at a static first frame; no media should autoplay. Give the avatar/gallery, close/back, action buttons, and mute control accessible names, logical focus order, and non-color-only mute state. Test long names, missing avatars, large text, keyboard navigation, and a background whose contrast changes under every supported app theme.
