### #135 — BE-007, the finding the cross-tier exchange produced
Not in the original 52. It surfaced because the frontend agent asked whether one-socket-per-account
was intentional. It was not.

`onlineUsers: Map<userId, socketId>` was set last-write-wins on connect, and every realtime emit
but one resolved recipients through it. **Opening a second tab silently deafened the first** — still
connected, still authenticated, no longer addressable. Push suppression read the same map, so if
the newer tab reported visible the push was suppressed too: the user looking at the older tab got
neither the message nor a notification. It did not self-heal on close.

`sessionRebuildNeeded` was the only room-addressed emit in the backend; the `user:<id>` join was
already there on connect and otherwise unused. It is now the delivery mechanism and the map is
deleted — which also retires the guarded-disconnect dance, since Socket.IO maintains room
membership itself. New seam: `backend/src/chat/utils/user-room.ts`.

**Two near-misses, both caught by advisory before merge, both worth remembering:**
1. Room-addressing ciphertext would have been a session-destroying bug. Signal decryption is not
   idempotent — it consumes the message key and advances the ratchet, and the client's tabs share
   one session store, so the second tab's decrypt of the same ciphertext FAILS into the client's
   decryption failure policy. `newMessage` and `messageEdited` therefore go to ONE tab via
   `emitToNewestTab`, reproducing the old target exactly. **Do not "tidy" these into room emits.**
2. The first fix for that made push suppression `.some()` across all tabs — incoherent with
   single-tab delivery, because a focused tab A would suppress the push while ciphertext landed on
   background tab B. Suppression now evaluates the *same* socket delivery uses. Lifting the
   carve-out must move both to room-wide in the same change.
