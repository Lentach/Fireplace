### C2-01 Socket.IO built-in reconnection left enabled, racing the app's ChatReconnectManager
- severity: High
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/services/socket_service.dart:21-31 ; cross-ref socket_io_client-2.0.3+1/lib/src/manager.dart:83,379-381
- evidence: |
    // socket_service.dart
    _socket = io.io(
      baseUrl,
      io.OptionBuilder()
          .setTransports(['websocket'])
          .setAuth({'token': token})
          .disableAutoConnect()
          .enableForceNew()
          .build(),
    );
    _socket!.connect();
    // manager.dart (package, verified): reconnection defaults to ON
    reconnection = options['reconnection'] != false;        // line 83
    ...
    if (reconnection == true && !skipReconnect!) { reconnect(); }   // line 379-381, on transport disconnect
- impact: |
    OptionBuilder calls `disableAutoConnect()` but never `disableReconnection()`, so the package Manager keeps
    `reconnection == true` (verified default, manager.dart:83) with `reconnectionAttempts = infinity`,
    `reconnectionDelay 1000ms`, `delayMax 5000ms`. On a non-intentional transport drop the package fires its OWN
    `reconnect()` (manager.dart:379) AT THE SAME TIME as the app's `onDisconnect` → `ChatReconnectManager.onDisconnect`
    → `_scheduleReconnect` → `connect()` (connection_provider.dart:165-179, 182-187). Two uncoordinated reconnect
    loops: the package retry reuses the SAME socket/Manager and fires `connect` again, while the app's `connect()`
    disposes that socket and builds a fresh one (socket_service.dart:14-18). The package loop ALSO ignores the app's
    2s `reconnectConnectCooldown` and exponential backoff, so on a flaky iOS PWA link this produces connect churn the
    "reconnect storm guard" (CLAUDE.md §84) was meant to prevent. The 2s cooldown only throttles the app path, not the
    package path.
- fix: |
    Add `.disableReconnection()` to the OptionBuilder so `ChatReconnectManager` is the single reconnection authority
    (it already owns backoff + the 2s cooldown). Then feed transport failures into it via a `connect_error` listener
    (see C2-03). This matches the documented design that "`ChatReconnectManager` ... reconnect[s] after disconnect"
    (chat_reconnect_manager.dart:5-6).

### C2-02 Built-in reconnect re-sends a STALE JWT after silent token refresh
- severity: High
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/providers/connection_provider.dart:259-262 ; cross-ref socket_io_client-2.0.3+1/lib/src/socket.dart:73,217
- evidence: |
    // connection_provider.dart — refresh updates reconnect/messaging token but NOT the live socket auth
    void applyRefreshedAccessToken(String newAccessToken) {
      _reconnectManager.tokenForReconnect = newAccessToken;
      _messagingProvider?.setToken(newAccessToken);
    }
    // socket.dart (package, verified): auth captured ONCE, re-sent verbatim on every (re)connect
    auth = opts!['auth'];                 // line 73 (construction)
    ...
    sendConnectPacket(auth);              // line 217 (every connect handshake)
- impact: |
    `applyRefreshedAccessToken` (wired from `AuthProvider.setOnAccessTokenChanged`, main_shell.dart:42) refreshes the
    reconnect/messaging tokens but never updates `_socketService.socket.auth`. The package socket captures `auth` once
    at construction (socket.dart:73) and resends that exact value on every handshake (socket.dart:217). Because
    built-in reconnection is still active (C2-01), a transport blip AFTER the 15-min silent refresh handshakes with the
    EXPIRED access token → server rejects the namespace connect → `CONNECT_ERROR` (socket.dart:300 maps it to the
    socket `error` event). On iOS PWA (long suspends + frequent token rotation) this surfaces as a connection that
    refuses to come back until a full relaunch, and (via C2-04) fails any in-flight send. The app's own `connect()`
    path is immune (it builds a new socket with the fresh token), so the bug only bites when the PACKAGE reconnects.
- fix: |
    Preferred: `.disableReconnection()` (C2-01) so only `connect()` — which always passes the current token — ever
    re-establishes the socket. Otherwise, in `applyRefreshedAccessToken`, also push the new token into the live socket
    (`_socketService.socket?.auth = {'token': newAccessToken}`) so the package handshake uses it.

### C2-03 No `connect_error`/`connect_timeout` handler; `_intentionalDisconnect` stays true until first `connect`
- severity: Medium
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/providers/connection_provider.dart:153-179,189-193
- evidence: |
    _intentionalDisconnect = true;
    _socketService.disconnect();
    _socketService.connect(baseUrl: baseUrl, token: token);
    _registerEventListeners();
    _socketService.onConnect(() => _onSocketTransportConnect(userId, token));
    _socketService.on('socketReady', (_) => _onSocketReady());
    _socketService.onDisconnect((_) {
      ...
      if (!_intentionalDisconnect) { _reconnectManager.onDisconnect(_scheduleReconnect, ...); }
    });
    // _onSocketTransportConnect is the ONLY place that clears the flag on the new socket:
    void _onSocketTransportConnect(int userId, String token) { ... _intentionalDisconnect = false; ... }
- impact: |
    Only the `disconnect` event drives the app's reconnect, and it is gated by `_intentionalDisconnect`, which is set
    `true` at socket replacement (line 153) and cleared ONLY on a successful `connect` (line 191). The handshake-failure
    events `connect_error`/`connect_timeout` have NO listener, so if the replacement socket never connects (server down
    at connect time, or auth rejected per C2-02), `ChatReconnectManager` never schedules a retry. Today this is masked
    only by the package's built-in reconnection — so the moment C2-01's recommended `disableReconnection()` is applied,
    a failed initial/replacement handshake becomes a permanent dead connection recoverable only by app relaunch.
- fix: |
    Register `_socketService.on('connect_error', ...)` (and `connect_timeout`) that, when `!_intentionalDisconnect`,
    routes into `_reconnectManager.onDisconnect(_scheduleReconnect, onMax)` — the same path the `disconnect` handler
    uses. Pair with C2-01 so the app owns all retry.

### C2-04 Any server `error` (incl. CONNECT_ERROR) fails ALL in-flight sends in the open chat
- severity: Medium
- confidence: High
- dimension: CORRECTNESS & STATE
- location: frontend/lib/providers/connection_provider.dart:472-479 ; cross-ref messaging_provider.send.dart:976-991, socket.dart:300
- evidence: |
    _socketService.on('error', (err) {
      final String msg = err is Map<String, dynamic> && err['message'] != null
          ? err['message'] as String
          : err.toString();
      _errorMessage = msg;
      _messagingProvider?.markSendingMessagesFailed(msg);
      notifyListeners();
    });
    // markSendingMessagesFailed marks EVERY sending row in the active conversation failed:
    final sending = _messages.where((m) => m.deliveryStatus == MessageDeliveryStatus.sending).toList();
- impact: |
    The single generic `error` handler fires for ANY server-emitted `error` — search/friend/key-bundle/timer ops,
    AND package-level namespace CONNECT_ERROR (socket.dart:300 re-emits it as `error`). Every such event flips ALL
    currently-"sending" messages in the open conversation to `failed` (messaging_provider.send.dart:977-989), even when
    the error is unrelated to those sends. A transient blip while a legit message is mid-flight presents the user a
    false "failed" message that may actually have been delivered (no tempId/ack correlation here).
- fix: |
    Correlate failures to the offending emit: have the server include the failing `tempId`/op in the error payload and
    fail only that row; or scope `markSendingMessagesFailed` to genuine send-rejection error codes rather than every
    `error`. Treat CONNECT_ERROR on the connection path (C2-03) separately from message-send errors.

### C2-05 `dispose()` omits `_resumeProbeTimer.cancel()` and `_intentionalDisconnect` — asymmetric with `disconnect()`
- severity: Low
- confidence: High
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/providers/connection_provider.dart:484-490 ; compare 266-270
- evidence: |
    @override
    void dispose() {
      _debouncedConnectTimer?.cancel();
      _reconnectManager.cancel();
      _socketService.disconnect();
      super.dispose();
    }
    // disconnect() DOES cancel the probe + set the flag:
    void disconnect({bool isLogout = false}) {
      _intentionalDisconnect = true;
      _debouncedConnectTimer?.cancel();
      _resumeProbeTimer?.cancel();          // <-- missing in dispose()
      _reconnectManager.cancel();
- impact: |
    `dispose()` cancels the debounce + reconnect timers but NOT `_resumeProbeTimer`, and does not set
    `_intentionalDisconnect`. If the 6s resume probe is armed when the provider is disposed, the timer fires post-dispose
    and calls `connect(...)` → `notifyListeners()` on a disposed `ChangeNotifier` ("used after being disposed"). In
    practice `ConnectionProvider` is a root `MultiProvider` entry (main.dart:73-77) living for the whole app, so this is
    a latent/teardown-only defect rather than a hot path — hence Low — but it is a real omission.
- fix: |
    Mirror `disconnect()` in `dispose()`: add `_intentionalDisconnect = true;` and `_resumeProbeTimer?.cancel();`
    before `_socketService.disconnect()`.

### C2-06 Resume fans out duplicate `getConversations`/`getMessages` emits (visibilitychange + lifecycle + chat reassert)
- severity: Low
- confidence: Medium
- dimension: RESILIENCE
- location: frontend/lib/screens/main_shell.dart:62-78,104-111 ; frontend/lib/providers/connection_provider.dart:327-335 ; frontend/lib/utils/chat_resume_reassert.dart:20-22
- evidence: |
    // main_shell visibilitychange handler:
    context.read<ConnectionProvider>().ensureReconnectIfNeeded();
    // main_shell didChangeAppLifecycleState.resumed:
    context.read<ConnectionProvider>().ensureReconnectIfNeeded();
    // _resyncAfterResume emits both:
    _socketService.getConversations();
    if (activeConvId != null) { _socketService.getMessages(activeConvId, limit: AppConstants.messagePageSize); }
    // chat_resume_reassert also re-fetches the open chat:
    messaging.getMessages(conversationId);
- impact: |
    On a single iOS PWA foreground, both the web `visibilitychange` listener (main_shell.dart:67) AND
    `AppLifecycleState.resumed` (main_shell.dart:108) call `ensureReconnectIfNeeded()` → `_resyncAfterResume()`, and
    `ChatDetailScreen` independently re-fetches the open chat (chat_resume_reassert.dart). That is up to ~3 redundant
    `getMessages` and 2 `getConversations` emits per resume. They are idempotent reads (and the probe self-cancels via
    `_resumeProbeTimer?.cancel()`), so the only cost is extra traffic/battery — but it is avoidable duplication.
- fix: |
    Debounce resume re-sync (single entry point), or skip the second `ensureReconnectIfNeeded` when one already ran
    within a short window — reuse the `_lastConnectStartedAt`-style guard already present for `connect()`.

### C2-07 SocketService emits are fire-and-forget; emits while `_socket == null` are silently dropped
- severity: Info
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/services/socket_service.dart:35-37,54-95,246-250
- evidence: |
    void on(String event, void Function(dynamic) callback) { _socket?.on(event, callback); }
    void sendMessage(...) { ... _socket?.emit('sendMessage', payload); }
    void disconnect() { _socket?.disconnect(); _socket?.dispose(); _socket = null; }
- impact: |
    Every emit uses `_socket?.emit(...)`. While the socket exists but is mid-connect, socket.io buffers and flushes on
    connect (acceptable). But after `disconnect()` sets `_socket = null` (logout, or the window inside `connect()` at
    connection_provider.dart:154 before the new socket is built), an emit becomes a no-op with no error and no queue —
    a send issued in that window is silently lost with only optimistic UI to show for it. Reliability of exactly-once
    send is owned by `MessagingProvider` (`_pendingSendContent`, tempId reconciliation); this is a note for that owner,
    not a defect in this chunk. Flagged for cross-reference with the messaging-provider review (RevMsgB).
- fix: |
    No change required in `SocketService`. Ensure `MessagingProvider` re-drives `_pendingSendContent` after
    reconnect/`socketReady` so emits dropped during a null-socket window are retried (verify in the messaging chunk).

## Chunk summary
Connection lifecycle is largely well-built — force-new + pre-dispose prevents duplicate listeners, `isReconnect`
preserves state, `socketReady`-gated fetches, the 2s cooldown, exponential backoff, and the 6s zombie-socket resume
probe all match the documented design. The material risks are at the package boundary: socket.io's built-in
reconnection is left enabled and races the app's `ChatReconnectManager` (C2-01), and that built-in path re-sends the
JWT captured at construction, so it handshakes with a stale token after silent refresh (C2-02). Secondary: no
`connect_error` handler (C2-03) and an over-broad `error`→`markSendingMessagesFailed` (C2-04).
