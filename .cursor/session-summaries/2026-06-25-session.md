# iOS composer focus "flash" — cosmetic mask (approach A) shipped (0.0.70)

**Date:** 2026-06-25

## What was done
Resolved the residual bug in `docs/review/ios-composer-keyboard-flash-handoff.md`: the brief
(<1s) page jump/flip on iOS PWA composer focus. The persistent jump was already fixed by the
viewport **pin** (0.0.68/69); the leftover **flash** could not be killed by the pin because
iOS does the focus scroll/pan on the **GPU compositor thread** while the pin counters it
**reactively from the main thread** (always ≥1 frame behind → it can only *undo* the jump,
never prevent it; the gap before the undo IS the flash).

Implemented the handoff's recommended **approach A (cosmetic mask)** — the lowest-risk path
that sidesteps compositor lag entirely:
- A **solid full-scene `position:fixed` `<div>`** in the theme chat background colour
  (`FireplaceColors.messagesAreaBg`) is painted from the **first touch** and covers the whole
  layout viewport (explicit height = max of `innerHeight`/`documentElement.clientHeight`/
  `vv.height+offsetTop`), so the visible window is always under it regardless of the OS pan.
- It **fades out (140ms)** once the viewport **settles** (`visualViewport`: keyboard-up AND
  `offsetTop ≤ 3` ⇒ the pin reconciled the pan) or after a **600ms safety timeout**. The jump
  happens invisibly underneath.
- A solid fill needs no frame-perfect tracking → the compositor lag is irrelevant.

Armed alongside the pin in `ChatInputBar`: `_preArmComposerViewportPin` (pointer-down; now
also early-returns on a re-tap of the already-focused field) + `_onComposerFocusForWebViewport`
(covers programmatic reply/edit focus; **gated on `!_sendJustFired`** so a send-refocus never
flashes). Hidden on blur / 700ms no-focus safety (drag-away) / dispose.

Constraints honoured: iOS-WebKit-only, focus-scoped, reverted (NOT the banned global
scroll-lock); no E2E send-path / `index.html` / Android change.

## UPDATE — REVERTED (same day, 0.0.73)
On-device, the mask did **not** kill the flash, and the post-0.0.68 stack regressed:
- The **pre-arm** fired the pin's `position:fixed` on **pointer-DOWN** → in a **browser tab**
  (`fireplace.ignorelist.com`) that bounced the browser's own toolbar on every composer tap.
- The **mask + stacked blur-teardown** made keyboard-**hide** laggy (show fast, hide slow).
- The residual flash persisted regardless.

Per user ("revert all changes from the jump→flash point"), rolled back to the **0.0.68
viewport-pin** state (`b936a39`, **0.0.73**):
- `git checkout 0c488f2 -- chat_input_bar.dart jump_probe_web.dart CLAUDE.md`; deleted
  `web_ios_composer_focus_mask{,_web,_stub}.dart` + its test.
- **Kept:** the pin (jump→flash), `onTapOutside`, collapse-guard, portrait guard, inset.
- Verified: `flutter analyze` clean (4 dirs); **44 input tests green** (E2E send-flow intact).

**Still OPEN:** the residual <1s focus flash (iOS compositor pan to Flutter's below-fold
`<textarea>`). Approach A (mask) is now retired as ineffective on device. Next attempt should
be **approach B** (reposition Flutter's editing element) or another non-invasive route — NOT
host `position:fixed`. `font-16` (iOS auto-zooms inputs <16px on focus) is a safe re-addable
1-liner that was reverted along with the batch. See the handoff brief.
