**Date:** 2026-07-29 — **P0 root-caused, fixed, RELEASED 0.0.139 / `15a368c`, smoke 5/5, since CONFIRMED in the field.**

- **Cause, proven by execution and confirmed in production.** The prefs backend's `reload()` reads the store, AWAITS, then clears its in-memory cache and refills it from the snapshot it took — a write landing in that window survives in the store but is **dropped from the cache**, so `getString` returns null for a record that is physically present. Raw-plugin proof: `READ CACHE: null / REAL STORE: PLAINTEXT`; at volume 3/89 lost from cache, **0/89 from the store**. A missed plaintext record re-decrypts a consumed ratchet key → `DuplicateMessage` → permanent `[Decryption failed]` while the only copy sits on disk. Matched the owner's log exactly (`kind: duplicate`, `persist: false`, 42 ids), and the messages came back after the fix.
- **Why a pre-existing hazard started firing:** web-only (the prefs backend reloads only when `kIsWeb`), 10 reload sites at 0.0.134 → **18**, plus `sweepDestroyablePlaintext`/`drainPurgeBacklog`/`reconcileStoredPlaintext`/`_startPlaintextSweepTimer`, **all four absent at `a00ab0f`**: a 60s timer and a launch drain/sweep/reconcile chain reloading while inbound decrypts persist.
- **Where the fix lives now:** `ContentKv.authoritativeSnapshot()`. `PrefsContentKv` answers only on web (`reload()` already paid for that `getAll()`; `debugForceAuthoritative` forces it under `flutter test`), the native encrypted store answers null because its view cannot be clobbered. **Enumerations deliberately stay on the cache** — see the root-cause summary's "Deliberately NOT changed" before touching them.
- **Second, independent data-loss bug fixed:** `saveDecryptedContent` built `{...data}` unconditionally, so the terminal-failure write replaced real plaintext and hydration (`decrypt.dart:411`) skipped it forever. Fails-before deterministically. Explains the 27 `badMac` rows (sender 60), **not** the 42.
- **Killed by measurement:** reconcile (replicated `findServedMessageIds` SQL → `SERVED 45/45`), expiry (18628/18629 broken with `expiresAt = 2026-08-11`; backend clock `toISOString()`, container+DB UTC), retention/LRU (both `markRetired`; retired ids are never decrypted, these were), quota (3 fresh records written at 15:10:44 UTC, no `DECRYPT_PERSIST_FAILED`), key format/codec (byte-identical), `_userId == null` (init completed before history decrypt).
- **Corrected:** "own records hydrated, inbound didn't" was NOT proven — own rows never enter the decrypt pass, so `HISTORY_DECRYPT_START {count: 12}` says nothing about them. Still worth asking the owner: do his **own sent** messages from today show text?
- `E2ePersistentDiag` was exactly at its 80 cap — the destruction window had already rotated out. The expiry sweep still logs nothing on success.
