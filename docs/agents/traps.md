## E2E / multi-device / recovery
- Registration lock is OPT-IN — arms only once `account_authorizations` has a row; a client that sees no `linkingEnabled` field fails CLOSED to the old gate (`2026-09-05-session-optin-lock-gate.md`).
- A `registrationId` may not change under an unchanged identity; the OTP replenishment path bypasses `upsertKeyBundle` so BOTH uploads carry the (lxiv) guard; residual `_reenrollAfterReset` has no in-flight latch — recorded, not fixed (`2026-08-30-session-bounded-gate-lxiv.md`).
- A warning the user cannot act on is a dead end; recovery state must survive a restart — read the THREE addenda (`2026-08-29-session-d1-d2-recovery.md`).
- A term added to a gate predicate needs an owner that clears it — read `clearAll()` when adding state to a process singleton (`2026-09-08-session-c7-final-review.md`).
- Login hardcoding `deviceId = 1` locked owners out after a reset — login resolves the LIVE PRIMARY; session gates deny only on an EXPLICIT `revokedAt`; `getServedMessageIds` answers a revoked device with SILENCE (`2026-08-21-session-t6-revocation.md`).
- Hostile `nextListVersion` inflation is bounded by a plausibility ceiling (`2026-08-26-session-t10-reset-addressability.md`).
- Wake delivers `hidden → inactive → resumed`; the privacy curtain is the DOM `#fp-curtain`, not a Flutter widget (`2026-09-06-session-passcode-wake-curtain-merge.md`).
- Multi-device permanent record: `.planning/multi-device/` (`FINISH-HERE.md`, `progress.md`, `task_plan.md`) and `docs/design/multi-device.md` §12 — not LATEST.
- **SETTLED 2026-09-13: messages sent AFTER a peer wipes/reinstalls are expected damage, not a receiver bug** — the backlog is gone for good, but the peer IS asked to re-key (`notifyPeer: true` in every observed row) and new messages decrypt once they confirm the new safety number; verdict, evidence and the ruled-out fixes are in `docs/runbooks/e2e-decryption-failed.md` Step 3G (`2026-09-13-session-post-wipe-fork-settled.md`).
- **`hadIdentityReset` is the unpersisted in-memory `needsKeyUpload` (`encryption_provider.dart:119`) — but the bundle upload does NOT clear it** (`:1469` only reads it; clear sites are `:1473`, `:4296`, `:4336`), so it stays TRUE for the whole minting process and the ordinary reinstall path DOES take the `identityReset` branch. `idReset:false` means a process that did not itself mint (FCM-woken). The earlier "can never take that branch" reading was wrong (`2026-09-13-session-post-wipe-fork-settled.md`).
- **A keyless login RE-MINTS on an UN-ENROLLED account and GATES on an enrolled one** — `encryption_service.dart:1166` throws `E2eIdentityIncompleteException` when `guard.exists && guard.linkingEnabled`; only `guard.exists` WITHOUT `linkingEnabled` reaches `IDENTITY_GUARD_UNLOCKED_REMINT` / `IDENTITY_MINTED {reason: server-bundle-unlocked-remint}` (`:1201-1208`). It is the identity-bootstrap guard, NOT a property of the door you logged in through — observed 2026-09-13 via "Nie pamiętam hasła" on an un-enrolled account, which is why that door looked like the cause (`2026-09-13-session-apk-drill-rerun.md`).
- **The durable E2E diag panel is reached by LONG-PRESSING the shield on Privacy & Safety** (`🔓 hacker mode`) — grouped failures + `DECRYPT_DECISION` rows that survive restarts; there is no other way to read `e2e_diag_persist_v1` on a release build (no root on the emulator's production image) (`2026-09-13-session-apk-drill-rerun.md`).
- `recordPeerIdentityChangedFromServer` needs a pinned anchor — call `buildSession` FIRST (`2026-09-12-session-c10-key-change-line-lifetime.md`).
- **A peer's account-identity anchor NEVER auto-advances from a server event** — `_demoteKeyChangeIfMuted` can only promote a candidate the device recorded (`encryption_service.dart:306-319`), so after your re-mint their FIRST send is refused with `AccountIdentityMismatch` and a red pill until a human confirms. By design (xlvi) — do not "fix" it (`2026-09-13-session-post-wipe-fork-settled.md`). Since 0.2.43 the pill no longer waits for that refusal: it renders for any peer in `peersWithChangedIdentity` whatever the key-change warnings setting says (`2026-09-13-session-unreadable-row-copy.md`).
- **Sending first does NOT spare the peer that confirmation** — device-proven: the peer decrypted the wiped device's PreKey message and its reply still bounced `AccountIdentityMismatch`; the outbound path validates the anchor regardless of an existing session (`2026-09-13-session-post-wipe-fork-settled.md`).
- **A recovery phrase is INERT on an un-enrolled account** — with 12 words saved but linking off, `pm clear` → log in re-mints silently and never offers the restore door; the door lives on the device-link gate. And `Włącz łączenie` forces REGENERATING the phrase even when one exists (`2026-09-13-session-post-wipe-fork-settled.md`).
- **A phrase restore REBINDS the device id** — a peer app already open keeps sending to the old id (`Bad state: Recipient has no key bundle (… deviceId=1)`) and shows the restored device's first message as `[encrypted]`; ONE reload of the peer app clears both (`2026-09-13-session-post-wipe-fork-settled.md`).
- **`hadIdentityReset` is process-wide and peer-AGNOSTIC** — during the whole life of a minting process it is true for EVERY peer, so an UNRELATED peer's transient `noSession`/`unknown` takes the `identityReset` branch: `markContentFailed: true`, `retryAction: none`, plus a `requestSessionRebuild` that peer never needed. Bounded (`persist: false`, so a later launch can recover the row) and not field-observed, but it is the strongest red-first test candidate in this area (`2026-09-13-session-post-wipe-fork-settled.md`).
- **The key-change pill is no longer gated on `keyChangeWarnings` (0.2.43)** — a peer in `peersWithChangedIdentity` means the anchor never advanced, which means every send to them fails closed, so the door must be visible BEFORE the user composes; the muted (lxxix) note is suppressed whenever the pill shows (`peerKeyChangeNoteAt` is computed under `!peerIdentityChanged`). Do not re-gate it on the setting (`2026-09-13-session-unreadable-row-copy.md`).
- **`[encrypted]` / `[Decryption failed]` are internal sentinels and must never render (0.2.43)** — relabel in `sentinelDisplayText` (`utils/message_display_text.dart`) ONLY: TWO surfaces draw a message body (the bubble's `TextMessageContent._displayBody` and `messageDisplayContent`, used by `ChatMessageBubble` and the provider-free long-press replica), they both delegate to it, and when they decided separately they disagreed — the replica localized `[Decryption failed]` while the bubble printed it raw. Display-only, never rewriting `MessageModel.content` (the failed label is persisted and the durable cache must keep seeing it). An OWN `[encrypted]` row needs the LITERAL, not `displayAsEncryptedPlaceholder`: a fan-out row carries no ciphertext for its own origin device (ix), so the predicate misses it. And resolve `AppLocalizations` lazily per branch — hoisting it crashed `bubble_redesign_test.dart`, which pumps a plain bubble with no localizations ancestor, once in the bubble and again in the helper (`2026-09-13-session-unreadable-row-copy.md`).
- **"Relabel in `sentinelDisplayText` ONLY" means the message BODY** — `utils/reply_preview_helper.dart` is a THIRD surface that matches the same literals by hand and answers `l10n.encryptedMessage` for a quote, deliberately (a quote is one line, it tries `getCachedDecryption` first, and it takes plain `String` labels so the provider can call it without a `BuildContext`). Same row therefore reads "nie można odczytać" in its bubble and "Wiadomość zaszyfrowana" when quoted — intended, do not "unify" it (`2026-09-13-session-unreadable-row-copy.md`).
- **`_markMessageFailed`'s `errorMsg` argument goes NOWHERE** — ~15 call sites in `messaging_provider.send.dart` compute a reason ("Image too large (max 20 MB)", the whole `_userFriendlySendError` ladder) and the method stores only `deliveryStatus: failed`; `markSendingMessagesFailed` drops its argument too. Do NOT "wire them up": they are unlocalized English and would ship into a Polish UI. The one reason a user needs is rendered instead from a per-ROW verdict (`MessagingProvider.sendRefusedForIdentity(tempId)`, written from the thrown `AccountIdentityMismatch`) AND the peer-level `peersRefusedIdentity` — the peer set ALONE blamed a key change for a timeout in the same chat. - **The permission set Play sees is the MERGED manifest, not ours** — `cd frontend/android && cmd /c gradlew.bat :app:processReleaseManifest` (no keystore needed) → `frontend/build/app/intermediates/merged_manifest/release/outputReleaseAppLinkSettings/AndroidManifest.xml`: 9 permissions where the source declares 3 (`2026-09-13-session-android-release-research.md`).
- **`light_compressor_v2` merges a `dataSync` foreground service we never start** — no `BackgroundConfig` is passed, yet Play would demand an FGS declaration + demo video for it; strip with `tools:node="remove"` or declare dead code (`2026-09-13-session-android-release-research.md`).
- **The link ceremony is SYMMETRIC and the match code is 6 DIGITS** — both sides display a code (`.web.p` / `.android.n`), either may scan or type the other's, and the primary approves; logging in never adds a device (`resolveLoginDeviceId` returns the live primary); an UN-ENROLLED account meets no gate and silently re-mints, so linking must be enabled on the primary FIRST (device-proven 2026-09-13) (`2026-09-13-session-android-release-research.md`).
- **Linking cannot be enabled from a browser TAB** — `devices_screen.dart:425` gates on `isInstalledDisplayMode()`, so a non-installed PWA sees only "Najpierw zainstaluj Umbra jako aplikację"; any instruction that says "turn on linked devices" MUST say "install the PWA first" (`2026-09-13-session-android-release-research.md`).
- **The device-link gate WAS coverable by a pushed route — fixed 0.2.42 (`23be77d`, #175)** — it is a `Stack` child (`main.dart`), so `DeviceLinkGateRouteGuard` now removes page routes pushed while gated; dialogs and the ceremony's scanner (`kLinkScanRouteName`) are deliberately kept. Do not "simplify" it back to the one-shot edge `popUntil`: a push never rebuilds `AuthGate` (`2026-09-13-session-android-release-research.md`).
- **`getNotificationAppLaunchDetails()` is sticky for the whole PROCESS and `PushService.initialize` runs on EVERY login** — that combination re-delivered one account's notification tap to the NEXT account; latched to once per process in `android_fcm_local_notifications.dart` (`2026-09-13-session-android-release-research.md`).
- **No APK has ever been published** (`gh release list` empty) — while that holds, Play App Signing can still adopt the existing `.jks` via PEPK; after the first sideload ships, a Google-generated cert means those installs can never update (`2026-09-13-session-android-release-research.md`).
- **The device-link gate only appears when the device holds NO local identity for that account — `pm clear`, NOT logout** — logging out and straight back in with the password lands in the normal shell, because the account's identity keys survive logout on that device. Reproduce the friend's-fresh-phone state with `pm clear` (drill re-run 2026-09-13 on `7818786…`).
- **Enabling linking FORCES a recovery phrase first** — `Włącz łączenie` routes to the recovery-key screen with NO "Później" escape; 12 words + a word challenge must be completed before the device becomes primary. Budget for it in user instructions (drill re-run 2026-09-13).
