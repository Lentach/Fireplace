### C3-01 Mobile DualStorage is single-store (secure only), not the dual-write/SP-fallback the docs claim
- severity: High
- confidence: High
- dimension: E2E / CLIENT CRYPTO
- location: frontend/lib/services/encryption/signal_stores.dart:30-46 ; frontend/lib/services/encryption_service.dart:19-22 ; frontend/CLAUDE.md:75
- evidence: |
    // signal_stores.dart — the ONLY write/read path
    Future<void> write({required String key, required String value}) async {
      if (kIsWeb) {
        final prefs = await _sharedPrefs;
        await prefs.setString('$_spPrefix$key', value);
      } else {
        await _secure.write(key: key, value: value);   // secure ONLY — no SP mirror
      }
    }
    Future<String?> read({required String key}) async {
      if (kIsWeb) { ... }
      else { return _secure.read(key: key); }            // secure ONLY — no SP fallback
    }

    // encryption_service.dart:19-22 (comment) claims the opposite:
    // "DualStorage: writes to both flutter_secure_storage ... AND SharedPreferences ...
    //  Reads try flutter_secure_storage first, then falls back to SharedPreferences."
    // CLAUDE.md:75 likewise: "Mobile: writes to both ... AND SharedPreferences (fallback);
    //  reads: secure first, then SP fallback."
- impact: |
    On Android native (a gate target) and iOS native there is NO SharedPreferences fallback for
    Signal identity/session/pre-key material — it lives in flutter_secure_storage alone. The
    documented mitigation that supposedly survives secure-storage eviction does not exist. Android
    Keystore-backed flutter_secure_storage has documented loss scenarios (Keystore reset on
    lockscreen/biometric change, some OEM backup/restore, reinstall), and on loss the session
    silently vanishes — exactly the "[decryption failed]" / SESSION_INVENTORY-drop class the TEMP
    probes are chasing. The class header doc (signal_stores.dart:9-16) is accurate (platform
    switch); the usage comment and CLAUDE.md describe behavior the code never performs.
- fix: |
    Either implement the documented mobile dual-write/dual-read (write secure AND
    `prefs.setString`; read secure, fall back to prefs) so the "DualStorage" name and the durability
    claim hold, OR correct encryption_service.dart:19-22 and CLAUDE.md:75 to match the actual
    platform-switch behavior. Given the active session-loss investigation, implementing the real
    mobile SP mirror is the higher-value option; mirror the kIsWeb branch's prefs usage already in
    `write`/`read`.

### C3-02 ensureSession: concurrent second caller hangs forever on pre-key-bundle timeout
- severity: High
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/providers/encryption_provider.dart:118-135
- evidence: |
    if (_pendingPreKeyFetches.containsKey(recipientId)) {
      await _pendingPreKeyFetches[recipientId]!.future;   // 2nd caller: RAW future, no timeout
      return;
    }
    final completer = Completer<Map<String, dynamic>>();
    _pendingPreKeyFetches[recipientId] = completer;
    ...
    final bundle = await completer.future
        .timeout(const Duration(seconds: 10), onTimeout: () {
      _pendingPreKeyFetches.remove(recipientId);
      throw TimeoutException('Pre-key bundle fetch timed out for user $recipientId');
    });
- impact: |
    Two near-simultaneous `ensureSession(recipientId)` calls (e.g. two quick sends to a session-less
    peer, or a drained offline queue) — caller A registers the completer and awaits
    `completer.future.timeout(...)`; caller B takes the `containsKey` branch and awaits the RAW
    `completer.future`. On timeout, `onTimeout` only throws into A's derived future and removes the
    map entry; it NEVER completes the source `completer`. A late `onPreKeyBundleResponse` then
    `remove`s null and returns (line 339-340), so the completer is orphaned and B's
    `await completer.future` never resolves. B's send/edit hangs permanently — message stuck SENDING
    with no failure, no retry, no plaintext (the single-caller "no plaintext fallback" invariant is
    fine; this is an extra concurrency defect). Affects both platforms.
- fix: |
    In `onTimeout`, complete the source completer with the error instead of throwing past it, e.g.
    `if (!completer.isCompleted) completer.completeError(TimeoutException(...));` then `return` /
    rethrow — this resolves BOTH the derived and the raw future. The repo already uses this pattern
    in `_cancelPendingFetches` (encryption_provider.dart:443-450) which calls `completer.completeError`.

### C3-03 One-shot media-key save-guard only inspects SharedPreferences, not the secure-storage legacy entry
- severity: Medium
- confidence: Medium
- dimension: E2E / CLIENT CRYPTO
- location: frontend/lib/services/encryption_service.dart:300-318 ; cf. getDecryptedContent 327-334
- evidence: |
    if (data['mediaKey'] == null) {
      final existingRaw = prefs.getString(key);        // checks SharedPreferences ONLY
      if (existingRaw != null) {
        try {
          final existing = jsonDecode(existingRaw) as Map<String, dynamic>;
          if (existing['mediaKey'] != null) return;    // refuse keyless overwrite
        } catch (_) {}
      }
    }
    await prefs.setString(key, jsonEncode(data));
    // getDecryptedContent reads prefs FIRST, then _storage fallback (327-334)
- impact: |
    The keyless-overwrite guard protects the irreplaceable media key only when the existing entry is
    in SharedPreferences. For users upgraded from a version that persisted decrypted content into
    flutter_secure_storage (the documented `getDecryptedContent` fallback, "written by older app
    versions"), the media entry lives in `_storage`, not prefs. A transient keyless re-decrypt
    (DuplicateMessage/Bad Mac storing `[Decryption failed]`) passes the guard (prefs empty), writes a
    keyless entry to prefs, and since `getDecryptedContent` reads prefs first, the good
    secure-storage media keys are permanently shadowed → voice/image unplayable forever. Narrow
    (upgrade-only) but it is exactly the irreversible loss the two-part fix exists to prevent.
- fix: |
    Make the guard mirror `getDecryptedContent`'s read order: check the existing entry via the same
    prefs→`_storage` fallback (or call `getDecryptedContent(id)`) before allowing a keyless write,
    so a legacy secure-storage media entry also blocks the downgrade.

### C3-04 E2E_INIT_FAIL writes a raw exception string into the user-copyable diagnostic log
- severity: Medium
- confidence: Medium
- dimension: SECURITY (client)
- location: frontend/lib/providers/encryption_provider.dart:306-311 ; sink frontend/lib/utils/e2e_diag_log.dart:8-14
- evidence: |
    } catch (e) {
      debugPrint('[E2E] Initialization failed: $e');
      if (!_e2eInitialized) _e2eInitialized = false;
      _e2eFlowLog('E2E_INIT_FAIL', {'error': e.toString()});   // arbitrary message, not id/bool
    }
    // e2e_diag_log.dart: _entries.add('$hh:$mm:$ss $step | $data');  // 200-entry ring, always on
- impact: |
    The brief requires the diag log (viewable + Copy button in Privacy & Safety) to be ids/booleans
    only. `E2E_INIT_FAIL` is the one event carrying an unbounded exception string. `initialize()`
    deserializes the stored identity key pair via `base64Decode` / `IdentityKeyPair.fromSerialized`;

    base64 of the PRIVATE identity key — into the message, which then lands in a log the user can
    copy/paste into a bug report. Sibling event `SESSION_STORE_WRITE_FAIL` already avoids this.
- fix: |
    Log only the exception type, matching the existing safe pattern in
    signal_stores.dart:279-280: `_e2eFlowLog('E2E_INIT_FAIL', {'err': e.runtimeType.toString()});`
    (keep the full `$e` in the kDebugMode-only `debugPrint`).

### C3-05 Decrypted-content cache prune does a full secure-storage/localStorage enumeration on every save
- severity: Medium
- confidence: High
- dimension: PERFORMANCE
- location: frontend/lib/services/encryption_service.dart:316-318, 404-418
- evidence: |
    await prefs.setString(key, jsonEncode(data));
    await _pruneDecryptedContentCache(prefs, userId);   // runs on EVERY saveDecryptedContent
    ...
    final keys = <String>{
      ...prefs.getKeys().where((key) => key.startsWith(prefix)),
      ...(await _storage.readAll()).keys.where((key) => key.startsWith(prefix)),  // full scan
    }.toList();
    if (keys.length <= _decryptedContentCacheLimit) return;   // early-return AFTER the scan
- impact: |
    `_storage.readAll()` on mobile is `_secure.readAll()` — it reads and decrypts EVERY Keychain/
    Keystore item (all Signal session/pre-key blobs), and on web enumerates+reads all `sig_`
    localStorage entries. It runs once per decrypted message (`saveDecryptedContent` is called per
    message in messaging_provider.decrypt.dart:141), and the cheap early-return happens only after
    the scan. During a history backfill of N messages that is N full keystore enumerations —
    measurable jank / battery on mobile, redundant since current writes all target prefs.
- fix: |
    Gate the expensive `_storage.readAll()`: compute the threshold from `prefs.getKeys()` alone
    (where all current entries live) and only fall back to a `_storage` scan when the prefs count is
    near the cap, or prune on an interval rather than every write.

### C3-06 Identity trust is unconditional TOFU — no MITM / key-substitution detection
- severity: Medium
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/services/encryption/signal_stores.dart:133-141 ; frontend/lib/services/encryption_service.dart:160-162
- evidence: |
    Future<bool> isTrustedIdentity(SignalProtocolAddress address,
        IdentityKey? identityKey, Direction direction) async {
      if (identityKey == null) return false;
      // Auto-update: accept key rotation ... TOFU always wins.
      await saveIdentity(address, identityKey);
      return true;                                    // every key, every time
    }
    // buildSession: await _identityStore.saveIdentity(address, identityKey); // trust bundle as-is
- impact: |
    Any identity key the server delivers in a pre-key bundle is accepted silently, including a
    changed key for an existing peer. A malicious/compromised key-distribution server can MITM or
    impersonate transparently; there is no safety-number comparison flow (`getIdentityFingerprint`
    returns only the LOCAL key for display, not a per-peer verification). For an app marketed as E2E
    this is a real trust-model gap. It appears intentional ("consumer app — we don't verify
    fingerprints manually"), so flagging for an explicit ship decision, not asserting a regression.
- fix: |
    Decide and document the trust model. If verification is desired, add a per-peer safety-number
    surfaced in Privacy & Safety and warn (rather than silently `saveIdentity`) when a known peer's
    identity changes; otherwise record the accepted limitation alongside the other E2E limits.

### C3-07 Provider decrypt()/encrypt() set _error + notifyListeners() on routine failures; _error never cleared on success and never surfaced
- severity: Low
- confidence: Medium
- dimension: CORRECTNESS & STATE
- location: frontend/lib/providers/encryption_provider.dart:82-92 (and 70-80)
- evidence: |
    Future<String> decrypt(int senderId, String ciphertext) async {
      try {
        return await _encryptionService.decrypt(senderId, ciphertext);
      } catch (e) {
        _error = 'Decryption failed: $e';
        notifyListeners();          // fires on every Bad Mac / Duplicate / NoSession
        rethrow;
      }
    }
- impact: |
    `decrypt` is the live-path decrypt used by messaging_provider.decrypt.dart:600, where Bad Mac /
    Duplicate / NoSession are NORMAL, expected terminal/retryable outcomes. Each one sets `_error`
    and calls `notifyListeners()`, so any listener of EncryptionProvider rebuilds on every failed
    decrypt (bursts during history backfill / the reset cascade). `_error` is never reset on a
    subsequent success (only on `onConnect`/`clearAll`) and is not displayed anywhere
    (`encryptionProvider.error` has no UI consumer — only `colorScheme.error` matches in the UI), so
    the state is effectively dead while still driving churn.
- fix: |
    Don't treat routine decrypt failures as provider error state: drop the `notifyListeners()` (and
    likely the `_error` assignment) from `decrypt`, or clear `_error` on the next success. The
    caller already classifies failures via `decideDecryptionFailure`; the provider need not surface
    them.

### C3-08 In-RAM decrypted-content cache is unbounded (no 2000 cap, preserved across reconnect)
- severity: Low
- confidence: High
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/providers/encryption_provider.dart:27-29, 183-185, 384-395
- evidence: |
    final Map<int, MessageModel> _decryptedContentCache = {};
    void cacheDecryption(int messageId, MessageModel msg) {
      _decryptedContentCache[messageId] = msg;            // no eviction
    }
    void onConnect(bool isReconnect) {
      ...
      if (!isReconnect) { _decryptedContentCache.clear(); ... }   // kept on reconnect
    }
- impact: |
    The persisted cache is capped at 2000 (`_pruneDecryptedContentCache`), but this RAM mirror has
    no cap and is cleared only on fresh connect / `clearAll` / explicit cache-clear — not on
    reconnect or back-nav. In a long-lived PWA session (days, many reconnects) it grows one
    `MessageModel` per decrypted message. Bounded by session activity, but unbounded in principle.
- fix: |
    Apply an LRU/size bound mirroring the persisted 2000 cap, or clear it alongside the persisted
    prune. Reference the existing cap constant `_decryptedContentCacheLimit`.

### C3-09 generateMorePreKeys defaults the next-id counter to 100, risking OTP id reuse with divergent keypairs
- severity: Low
- confidence: Medium
- dimension: E2E / CLIENT CRYPTO
- location: frontend/lib/services/encryption_service.dart:219-238 ; cf. fresh-install 91-100
- evidence: |
    final nextIdStr = await _storage.read(key: 'e2e_${uid}_next_pre_key_id');
    final nextId = int.parse(nextIdStr ?? '100');        // counter lost -> assume 100
    final preKeys = generatePreKeys(nextId, _preKeyBatchSize);   // batch of 100
- impact: |
    Fresh install sets the counter to 20 and OTP ids start at 0. If only the `next_pre_key_id` entry
    is lost (selective storage eviction) while previously generated keys (e.g. ids 100-119 from an
    earlier replenish) survive, the default 100 regenerates ids 100-199 with NEW keypairs. The
    server still advertises the OLD public keys for 100-119; a peer that consumes one of those OTPs
    builds X3DH against a private key we overwrote → shared-secret mismatch → permanent Bad Mac for
    that session. Narrow (requires isolated counter loss) but it is silent key reuse.
- fix: |
    Derive the next id from the actual stored pre-keys (max existing `pre_key_*` id + 1) rather than
    a hardcoded 100 default, or persist the counter atomically with the batch write.

## Chunk summary
The crypto-policy core (terminal-failure precedence, no-delete-on-inbound, selective key deletion, media-key one-shot guard for current entries, envelope, 2000-cap eviction) is well-built and the documented terminal/rebuild invariants hold in-chunk. The ship-relevant gaps are durability/resilience: the "DualStorage" mobile path is single-store despite docs claiming an SP fallback (C3-01), and concurrent `ensureSession` callers can hang forever on a bundle timeout (C3-02). Plus a narrow media-key downgrade for upgraded users (C3-03), a diag-log exception-string leak (C3-04), an O(N) keystore scan on the decrypt hot path (C3-05), and unconditional identity TOFU (C3-06).
