### C11-01 Recorder stop/dispose run outside the re-entrancy try/finally — a stop failure permanently bricks the composer
- severity: High
- confidence: Medium
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/widgets/input/recording_controller.dart:413-499 (stopAndSend), 502-538 (cancelRecording)
- evidence: |
    // stopAndSend — awaits BEFORE the try that owns the finally:
    416    _isStopping = true;
    ...
    427    final recorder = _audioRecorder;
    428    if (recorder != null) {
    429      path = await recorder.stop();      // can throw
    430      await recorder.dispose();          // can throw
    431    }
    432    _audioRecorder = null;
    434    setState(() => _isRecording = false);
    ...
    443    try {
    ...
    496    } finally {
    497      _isStopping = false;
    498    }

    // cancelRecording — no try/finally at all:
    505    _isStopping = true;
    ...
    518    if (recorder != null) {
    519      await recorder.stop();             // can throw
    520      await recorder.dispose();
    521    }
    ...
    537    _isStopping = false;                 // unreachable if 519 throws
- impact: If `AudioRecorder.stop()`/`dispose()` throws (native PlatformException on an interrupted/invalid recorder state, hardware glitch, call interruption), `_isStopping` is never reset and `_isRecording` stays true. Both `stopAndSend` and `cancelRecording` early-return while `_isStopping` is true (414, 503), so the recording bar stays on screen forever and the user can neither send nor cancel — the composer is dead until they leave the chat, and the recording is lost. The exception is also an unhandled async error (callers at chat_input_bar.dart:602 and the 120s timer at recording_controller.dart:389 do not await/catch). Affects iOS PWA and Android native.
- fix: Wrap the `recorder.stop()/dispose()` awaits in the same try whose `finally` resets `_isStopping` (and reset `_isRecording`/`_audioRecorder` in that finally). The correct pattern already exists in this file: `_releaseRecorderSilently` (223-246) wraps both calls in `try/catch`. `cancelRecording` should additionally gain a `try { ... } finally { _isStopping = false; }`.

### C11-02 stopAndSend/cancelRecording setState after `await` with no `mounted` guard — setState-after-dispose + double stop when leaving chat mid-stop
- severity: Medium
- confidence: Medium
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/widgets/input/recording_controller.dart:429-434, 495, 519-531
- evidence: |
    429      path = await recorder.stop();
    430      await recorder.dispose();
    431    }
    432    _audioRecorder = null;
    434    setState(() => _isRecording = false);   // no `if (!mounted) return;`
    ...
    495      setState(() => _recordingPath = null);
    // cancelRecording:
    519      await recorder.stop();
    520      await recorder.dispose();
    ...
    531    setState(() { _isRecording = false; _recordingPath = null; });
- impact: `startRecording` checks `if (!mounted) return;` after every await (281, 307, 316, 341, 356), but `stopAndSend`/`cancelRecording` do not. If the user pops the chat screen during the stop window (notably the web `http.get(blobUrl)` await at 470, which is network-bound), `dispose()` runs at the await boundary — it sees `_isRecording == true` and calls `_releaseRecorderSilently()` → `recorder.stop()` a second time on the same (possibly already-stopped) recorder, then control returns and `setState()` throws "setState() called after dispose()". A red-screen/console error and a double-stop on teardown.
- fix: Add `if (!mounted) return;` immediately after each `await recorder.stop()/dispose()` and after the web `http.get`, mirroring `startRecording`'s post-await guards; null out `_audioRecorder` before the await so the dispose-path branch (186-194) does not double-stop.

## Chunk summary
Composer/input widgets are well-structured (correct trailing-Stack invariant, `_isStarting`/`_isStopping` guards present, send-ordering contract honored, complete dispose in the parent). The one ship-relevant defect is **C11-01**: `recorder.stop()/dispose()` run outside the `_isStopping` try/finally (and `cancelRecording` has no finally), so a stop-time throw permanently bricks the recording bar and loses the clip on the voice-send critical path. **C11-02** (missing `mounted` guards after the stop awaits) is the related lifecycle gap. Remaining items are Low/Info polish (edit-vs-staged precedence, draft loss, empty-edit no-op, one hardcoded string, temp diagnostics, frame-rate waveform).
