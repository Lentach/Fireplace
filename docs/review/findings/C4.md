### C4-01 socket `error` event fails ALL in-flight sends, racing the still-pending emit → false "failed" flash + retry-duplicate
- severity: Medium
- confidence: Medium
- dimension: RESILIENCE
- location: frontend/lib/providers/messaging/messaging_provider.send.dart:963-992 and :819,:908 ; trigger: frontend/lib/providers/connection_provider.dart:472-479
- evidence: |
    // connection_provider.dart — fires while socket is STILL connected (app-level error)
    _socketService.on('error', (err) {
      ...
      _messagingProvider?.markSendingMessagesFailed(msg);
    });

    // send.dart — releases the exactly-once latch for every sending row
    void markSendingMessagesFailed(String errorMsg) {
      final sending = _messages.where((m) => m.deliveryStatus == MessageDeliveryStatus.sending)...
      for (final msg in sending) {
        final tid = msg.tempId;
        if (tid != null) _emittedSendTempIds.remove(tid);   // latch released
        ... copyWith(deliveryStatus: MessageDeliveryStatus.failed);
      }
    }

    // send.dart _encryptAndSend — latch acquired at 819, emit at 908 with awaits in between
    if (!_emittedSendTempIds.add(tempId)) { ...return false; }   // 819
    await _encryptionProvider!.ensureSession(recipientId);        // 878
    final ciphertext = await _encryptionProvider!.encrypt(...);   // 882
    _emit?.call('sendMessage', emitPayload);                      // 908  (no re-check of latch/failed)
- impact: A server `error` event (which may be unrelated to the current send — it sets a global `_errorMessage` and marks EVERY sending row failed) that lands during the `ensureSession`/`encrypt` await window will (a) flash the message as "failed" even though its `sendMessage` emit then fires and the server delivers it, and (b) clear the `_emittedSendTempIds` latch. The message normally auto-reconciles to "sent" when `messageSent` arrives, but if the user taps Retry inside that window, `_encryptAndSend` re-encrypts (latch is free) and re-emits, delivering a DUPLICATE to the recipient (the second copy advances the ratchet; on the peer it may surface as a terminal `[Decryption failed]`). The exactly-once invariant the latch exists to protect ("failed ⟹ not emitted") is violated by this race. Both platforms.
- fix: Make `markSendingMessagesFailed` scope-aware — only fail sends that have NOT yet passed the emit point, or re-check `_emittedSendTempIds.contains(tempId)` immediately before `_emit?.call('sendMessage', …)` (line 908) and abort the emit if the latch was cleared mid-flight. Better: have the backend `error` payload carry the failing `tempId`/`recipientId` so a single failed send is marked rather than the whole sending set (mirror the per-tempId reconcile already used in `_addMessageToState`).

### C4-02 Retry of a failed IMAGE/GIF/FILE that failed before upload finished is a silent no-op (stuck "failed" bubble)
- severity: Medium
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/providers/messaging/messaging_provider.send.dart:626-675 (image), :677-708 (gif), :710-763 (file); contrast voice fallback :607-622; retry entrypoint wired at frontend/lib/widgets/message/chat_message_bubble.dart:108-110
- evidence: |
    if (message.messageType == MessageType.image) {
      final iUrl = message.mediaUrl;
      final iKey = message.mediaKey;
      final iIv = message.mediaIv;
      if (iUrl != null && iUrl.isNotEmpty && iKey != null && iIv != null) { ...return; }
      if (message.mediaUrl != null &&
          (message.mediaUrl!.contains('cloudinary') || message.mediaUrl!.contains('/media/'))) {
        ... _encryptAndSend(... messageType: 'IMAGE', mediaUrl: message.mediaUrl);
      }
      return;   // <- mediaUrl == null (upload failed before it was set): both ifs false, no-op
    }
- impact: When `sendImageMessage`/`sendGif`/`sendFileMessage` throw during `encryptAndUpload` (network drop, oversize race, server 5xx), `_markMessageFailed` keeps the optimistic bubble in `failed` state but `mediaUrl` was never set (it's assigned only after a successful upload at send.dart:163-167/447-451). Tapping the Retry button calls `retryFailedMessage` → the type branch finds no url/keys and no cloudinary/`/media/` url → `return` with no re-attempt and without even resetting the row to `sending`. The bubble is a permanent dead-end: Retry visibly does nothing. Voice handles this with a `localAudioPath` fallback (:607-622) that re-runs `sendVoiceMessage`; image/gif/file discard the original `XFile`/bytes so no re-upload is possible. Both platforms; image is the common case (clipboard/picker send on a flaky connection).
- fix: Either retain the source bytes for image/gif/file on the optimistic message (or in `_pendingSendContent`) so retry can re-run `encryptAndUpload` like the voice `localAudioPath` path, or — minimally — surface that a media send is unrecoverable (disable/relabel Retry, prompt re-pick) instead of a no-op. Follow the voice branch pattern in `retryFailedMessage`.

### C4-05 Per-session memory growth: `_conversationCache` (no per-conv cap/eviction) and `_decryptChainBySender` cleared only on logout
- severity: Low
- confidence: High
- dimension: PERFORMANCE
- location: frontend/lib/providers/messaging_provider.dart:140 (_decryptChainBySender), :170 (_conversationCache); cleared only in clearAll :518,:533; cache writers at history.dart:32-53,:227-236
- evidence: |
    final Map<int, Future<void>> _decryptChainBySender = {};
    ...
    /// Cleared only on logout (clearAll).
    final Map<int, List<MessageModel>> _conversationCache = {};
    // clearAll(): _conversationCache.clear(); _decryptChainBySender.clear();
- impact: `_conversationCache` keeps the decrypted message list for every conversation the user visits for the whole session (survives back-nav and reconnect by design), with no per-conversation message cap and no LRU eviction. For a heavy user who opens many long chats in one session, RAM grows monotonically until logout. `_decryptChainBySender` is bounded by distinct sender count (small) and only holds completed futures, so it is not a true leak — noted for completeness. - fix: If field reports show memory pressure, bound `_conversationCache` with an LRU (keep N most-recent conversations, evict the rest — they reload from server/persisted plaintext on reopen) and/or cap retained messages per conversation to the paginated window. ### C4-07 `messages` getter exposes the live mutable list; reply-quote re-enrichment is O(n) on every decrypt/edit
- severity: Info
- confidence: High
- dimension: PERFORMANCE
- location: frontend/lib/providers/messaging_provider.dart:208 (getter), :249-256 (_reEnrichAllReplyQuotes); per-live-decrypt notify at messaging_provider.events.dart:114,127
- evidence: |

    void _reEnrichAllReplyQuotes() {

- impact: `_reEnrichAllReplyQuotes()` scans the entire loaded list (and for each row, `_enrichReplyPreview` re-looks-up the referenced message) and is invoked on every successful live decrypt, every edit, and at the end of each history pass; combined with one `notifyListeners()` per live-decrypted message it makes incoming-burst handling O(n·m).
