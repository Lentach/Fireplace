# Session 2026-05-09

## What was accomplished

User reported PWA auto-logging out users after ~24h, breaking push notifications (tap a push -> open PWA -> login screen instead of the message). Root cause traced and a two-phase fix is in motion.

### Investigation
Diagnosed root cause as `signOptions.expiresIn: '24h'` in `backend/src/auth/auth.module.ts` combined with `AuthProvider._loadSavedToken` clearing the stored token on any `/users/me` 401. No refresh mechanism, no sliding expiration, no per-device revocation. Token stored only in `SharedPreferences` (web -> localStorage).

### Brainstorming + research
Followed the `brainstorming` skill end-to-end. Compared session models in WhatsApp / Telegram / Signal / Discord / Slack via web research (sources: WebKit ITP docs, Discord OAuth2 docs, Slack token rotation docs, totalshiftleft.ai 2026 patterns, Akousa "Modern Auth 2026"). Findings:

- Telegram: 12-month sessions
- Slack (no rotation): never expires
- Discord: 7-day access + single-use refresh tokens
- Signal/WhatsApp: identity-key based (no JWT at all), challenge-response per request
- iOS PWA storage: 7-day ITP eviction does NOT apply to Home Screen apps
- Industry minimum: refresh-token rotation; messenger-grade: identity-key auth

User's preference: match E2E security with auth security -> chose Signal-style identity-key auth.

### Design spec (Phase 1)
Wrote `docs/superpowers/specs/2026-05-09-identity-key-auth-design.md` (~770 lines) covering:

1. Architecture (separate Ed25519 auth keypair, 2h JWT session token, in-memory challenge store, `device_sessions` table)
2. Detailed flows (registration, login, silent refresh, normal request, logout, remote logout, recovery, password change, socket auth)
3. Database schema (new `device_sessions`, no changes to `users`)
4. Backend implementation (file layout, endpoints, guards, Ed25519 verifier)
5. Frontend implementation (`AuthIdentityKeyPair` with DualStorage, `AuthSessionManager` with single-flight refresh)
6. Migration: NONE (small user base, everyone re-logs in once after deploy)
7. Testing strategy (Jest + Flutter test + manual E2E + edge cases)

Spec was reviewed by user; 10 substantive issues fixed inline:
- PostgreSQL partial-index `WHERE NOW()` removed (non-immutable)
- Timestamp wire format spelled out (Unix milliseconds, ±60s tolerance)
- 401 retry ordering rewritten (`forceRefresh()` preserves keypair, only second 401 triggers hard logout)
- Ed25519 seed vs full secret expansion clarified (`cryptography ^2.7.0` API)
- Per-IP + per-deviceId throttling added on `/auth/challenge` and `/auth/refresh-with-key`
- Multi-instance deployment checklist added (in-memory store -> Redis/DB before scaling)
- Guard migration list (5 controllers) + `req.user` shape change (`deviceId` added, `profilePictureUrl` dropped)
- Mid-connection token expiry: client-driven via Timer (not server-poll)
- Push notification subscriptions survive re-login (keyed by userId)
- Additional test cases: clock skew, smoke test, synchronize, multi-tab refresh, challenge griefing

## Final decision (end of session)

After the spec + plan were both written, user asked the pragmatic question: "is Phase 1 actually necessary, safe, and a real security improvement?". Honest re-evaluation:

- **Necessary?** No — Phase 0 already fixes the user-reported PWA auto-logout. Phase 1 fixes theoretical issues nobody reported.
- **Real security gain on web?** Modest. Stolen-token window 30d → 2h (15× shorter) and per-device revoke are real wins. But the "private key invisible to attacker" benefit doesn't materialize on web because `flutter_secure_storage_web` keeps keys extractable; XSS gets both JWT and key. Native (iOS/Android app) would be where the cryptographic device binding really matters.
- **Risk?** Real production risk: 30-task refactor in critical auth path, breaking change, single-pod constraint via in-memory challenge store, edge cases (clock skew, multi-tab, mid-session refresh).

**Decision: DEFER Phase 1.** Spec and plan stay as-is — they are complete reference material and can be re-opened when one of these triggers fires:
- Native iOS/Android app is launched (device binding becomes materially valuable)
- "Active Devices" UI is wanted as a product feature
- Threat model changes (specific attacker concerns surface)

Both spec and plan files were updated with explicit "deferred" status headers so future sessions don't accidentally re-execute them assuming approval was final.

**Higher-ROI alternatives identified for similar effort budget (not committed yet — user declined to schedule them this session):**
- 2FA / TOTP (~2-3 days) — phishing resistance
- RS256 JWT signing with split keys (~1 day) — `JWT_SECRET` leak no longer fatal
- Audit log with "new device login" alerts (~2 days) — user-side detection
- Per-username brute-force rate limit on `/auth/login` (~0.5 day)
