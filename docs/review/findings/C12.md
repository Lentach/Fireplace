### C12-01 Decrypted image bytes decoded at full native resolution (no cacheWidth/cacheHeight)
- severity: Medium
- confidence: High
- dimension: PERFORMANCE
- location: frontend/lib/widgets/message/image_message_content.dart:121-126 (also gif_message_content.dart:189-195 native path)
- evidence: |
    child: Image.memory(
      bytes,
      fit: BoxFit.cover,
      width: double.infinity,
      height: 220,
    ),
- impact: Each received image is decoded into the image cache at its full sender-supplied resolution even though it is only ever painted into a 220px-tall bubble. A long chat history with many photos holds many full-res decoded bitmaps simultaneously → high memory growth and GC churn, and on low-end Android-native devices a realistic OOM / jank risk while scrolling. The 20MB pre-decode byte cap (`MediaCryptoService.maxBytes`) bounds source bytes, not the decoded ARGB footprint (a 4000×3000 JPEG decodes to ~48MB regardless of source size).
- fix: Pass `cacheWidth` (and/or `cacheHeight`) to `Image.memory` sized to the painted box × `MediaQuery.devicePixelRatio` so Flutter downsamples at decode time. GIF native frames need full data, but the static `IMAGE` path here can safely downsample. Mirror the explicit 220px sizing already present.

### C12-02 Web GIF blob URL leaked when widget is disposed mid-load
- severity: Medium
- confidence: High
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/widgets/message/gif_message_content.dart:98-104, 38-44
- evidence: |
    if (kIsWeb) {
      final blobUrl = gif_blob.createGifObjectUrl(bytes);   // always runs
      if (mounted) setState(() => _objectUrl = blobUrl);     // skipped if unmounted
      return _GifDisplay.network(blobUrl);
    }
    // dispose():
    if (_objectUrl != null) { gif_blob.revokeGifObjectUrl(_objectUrl); }
- impact: On web, if the bubble is disposed (fast scroll / leave conversation) after fetch+decrypt resolves but before `setState` runs, `createGifObjectUrl` has already allocated a blob URL while `_objectUrl` stays null, so `dispose()` never revokes it. The blob is retained by the browser until full page reload. A GIF-heavy session accumulates orphaned object URLs → unbounded blob-store memory growth on the iOS PWA.
- fix: Capture the created URL before the mounted check and revoke it when unmounted, e.g. `if (!mounted) { gif_blob.revokeGifObjectUrl(blobUrl); return const _GifDisplay.error(); }` before assigning. Same revoke-or-assign discipline the `didUpdateWidget` path (lines 53-56) already follows.

### C12-04 Link tap fires unawaited `launchUrl(Uri.parse(...))` with no error handling
- severity: Medium
- confidence: High
- dimension: UX READINESS
- location: frontend/lib/widgets/message/text_message_content.dart:44-52 (and the link-preview card tap, 83-87)
- evidence: |
    final url = match.group(0)!;
    ...
      recognizer: TapGestureRecognizer()
        ..onTap = () =>
            launchUrl(Uri.parse(url), mode: LaunchMode.externalApplication),
- impact: `onTap` is synchronous and the `Future<bool>` from `launchUrl` is neither awaited nor try/caught. `url_launcher` throws a `PlatformException` when no handler app exists or returns `false` when launch fails; the message text gives no feedback and the failure becomes an unhandled async error (FlutterError in prod logs, silent dead-tap to the user). The URL regex `https?://[^\s]+` is greedy, so trailing punctuation (`https://x.com).`) is captured into the launched URI, opening a wrong/404 link. Note: scheme-injection XSS is NOT possible here — the regex only matches `http(s)://`, and Flutter renders via `RichText` spans (no HTML interpretation), so there is no innerHTML/JS surface.
- fix: Make the handler `async`, `await canLaunchUrl`/wrap `launchUrl` in try/catch, and on failure show `showTopSnackBar` (pattern already used in file/audio failure paths). Trim trailing punctuation from the matched URL before `Uri.parse`.

### C12-13 PlaybackController stream subscriptions are never explicitly cancelled
- severity: Low
- confidence: High
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/widgets/audio/playback_controller.dart:96-137
- evidence: |
    _player.stateStream.listen((state) { ... });
    _player.positionStream.listen((position) { ... });
    _player.durationStream.listen((duration) { ... });
    ...
    @override
    void dispose() {
      VoiceAudioCoordinator.instance.onStoppedPlaying(this);
      _player.dispose();
      super.dispose();
    }
- impact: Three `listen()` subscriptions are created in `initState` and their `StreamSubscription`s are dropped (never stored/cancelled). No leak occurs today because both implementations close their streams on `dispose()` — native delegates to `just_audio` `AudioPlayer.dispose()`, and `WebVoicePlayer.dispose()` explicitly `.close()`s all three controllers (voice_player_web.dart:237-245) — which terminates the listeners. The `mounted` guards also prevent setState-after-dispose. This is correct but fragile: any future player impl that forgets to close a stream silently leaks a listener holding `this`.
- fix: Store the `StreamSubscription`s and cancel them in `dispose()` before `_player.dispose()`, making cleanup independent of the player contract.

## Chunk summary

Message-rendering, context-menu, and audio widgets are well-structured and security-aware: text links are http(s)-only (no HTML/JS injection surface in Flutter's `RichText`), and media fetches are host-allow-listed with the JWT sent only same-origin (`fetchMediaBytes` H-04, verified). No Blocker/High issues found. The most actionable items are a web GIF blob-URL leak on dispose-mid-load (C12-02), full-resolution image decode with no `cacheWidth` on the chat hot path (C12-01), the global context-menu overlay lacking a lifecycle tie to its screen (C12-03), and an unguarded fire-and-forget `launchUrl` (C12-04); the rest are i18n gaps and polish. Both top-level files are confirmed re-export shims only.
