### C8-01 SW `message` handler does no source/origin validation
- severity: Low
- confidence: High
- dimension: SECURITY (client)
- location: frontend/web/web-push-sw.js:252-284
- evidence: |
    self.addEventListener('message', function (event) {
      var data = event.data;
      if (!data) return;
      var work = null;
      if (data.type === 'clear-badge') { work = setBadgeFromSW(0); }
      else if (data.type === 'set-badge') { work = setBadgeFromSW(...); }
      else if (data.type === 'close-conv') { ... closeNotificationsForTag(...) ... }
      else if (data.type === 'sweep') { ... sweepStaleNotifications(ids) ... }
- impact: No `event.origin`/`event.source` gate before acting on badge/tray ops.
    In practice low risk — ServiceWorker `message` events are same-origin-only by
    platform (a cross-origin page cannot `postMessage` to this SW), and the ops
    only manipulate the app badge / notification tray (no data exfiltration). Worth
    a defensive note, not a blocker.
- fix: Optional hardening — early-return unless `event.source` is a `WindowClient`
    of this origin. Document the same-origin assumption inline so a future
    contributor doesn't add a sensitive op here without a gate.

### C8-02 `pushsubscriptionchange` has no SW-side re-subscribe; rotation while PWA closed silently kills push
- severity: Low
- confidence: Medium
- dimension: RESILIENCE
- location: frontend/web/web-push-sw.js:288-296
- evidence: |
    self.addEventListener('pushsubscriptionchange', function (event) {
      event.waitUntil(
        clients.matchAll({ type: 'window', includeUncontrolled: true }).then(function (clientList) {
          for (var i = 0; i < clientList.length; i++) {
            clientList[i].postMessage({ type: 'push-subscription-change' });
          }
        })
      );
    });
- impact: When the browser rotates/expires the push subscription while the PWA is
    closed (no window clients), the loop posts to nobody and the SW does not
    re-subscribe itself. Push notifications then silently stop until the user next
    opens the app and the page-side handler re-syncs. For a messenger this means
    missed-message alerts after a rotation. Not in the documented accepted-limits
    list. (Mitigation: live-app re-sync is page-side and out of this chunk; SW-side
    re-subscribe is hard because it needs the VAPID `applicationServerKey` embedded.)
- fix: Consider re-subscribing inside the SW using the stored
    `applicationServerKey` (`registration.pushManager.subscribe(...)`) and POSTing
    the new endpoint, falling back to the current page-notify path. At minimum
    document this as an explicit known limit alongside the other iOS push notes in
    frontend/CLAUDE.md §6.

### C8-03 No Content-Security-Policy on the app shell of an E2E messenger
- severity: Low
- confidence: Medium
- dimension: SECURITY (client)
- location: frontend/web/index.html:1-40 (absence of any CSP meta)
- evidence: |

    <meta content="IE=Edge" http-equiv="X-UA-Compatible">
    <meta name="viewport" content="...">
    <meta name="description" content="Fireplace - real-time messenger">
    (no <meta http-equiv="Content-Security-Policy" ...> present)
- impact: For an E2E app, a missing CSP removes a defense-in-depth layer against
    injected/3rd-party script and unexpected connect/img origins. DOM-XSS surface

- fix: Confirm a CSP (script-src/connect-src restricted to the API + push origins,
    allowing the wasm/worker needs of CanvasKit) is served by nginx; if not, add one.
    Reference the existing nginx header setup rather than a meta tag.

### C8-05 manifest omits `id` (and explicit `scope`)
- severity: Info
- confidence: High
- dimension: PWA / WEB
- location: frontend/web/manifest.json:1
- evidence: |
    {"name":"Fireplace","short_name":"Fireplace","start_url":".","display":"standalone",
     ... "orientation":"portrait-primary","prefer_related_applications":false,"icons":[...]}
- impact: No `id` field — the PWA identity then derives from `start_url`, so a
    future `start_url` change would be treated by the browser as a *different* app
    (duplicate install). No explicit `scope` (defaults to the `start_url` directory
    `/`, which is correct here). Neither breaks the current root deploy.
- fix: Add a stable `"id":"/"` (or a fixed string) and an explicit `"scope":"/"`
    to lock app identity and navigation scope.

### C8-09 (cleared) Push-only SW: no app-shell caching → no stale-bundle risk from this SW
- severity: Info
- confidence: High
- dimension: PWA / WEB
- location: frontend/web/web-push-sw.js (handlers: push:134, notificationclick:200, message:252, pushsubscriptionchange:288)
- evidence: |

- impact: None — recorded to answer the brief's cache/update questions. This SW

    separate Flutter-generated SW at scope `/` (out of this chunk). Because the push

    `skipWaiting()`/`clients.claim()`. Update propagation is correct.
- fix: None. (If desired, add a comment noting the empty-scope activation behaviour
    so a future contributor doesn't add `skipWaiting` cargo-culted from app SWs.)
