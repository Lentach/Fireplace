### C7-01 Baked-in default VAPID key masks a missing build define (no fail-fast)
- severity: Medium
- confidence: Medium
- dimension: BUILD/RELEASE
- location: frontend/lib/services/push_service.dart:48-56
- evidence: |
    // TODO: Replace with your real VAPID key.
    static const String _vapidKey = String.fromEnvironment(
      'WEB_PUSH_VAPID_PUBLIC_KEY',
      defaultValue:
          'BOkbC_6t7ScCiTLyuLyM0wEG3TnXfpQaAMwZUeJHuWhtt7HVr0u3zG60xm4kqqhnNzuHZco-8h0Nt_WRYRZrZHU',
    );
    // deploy-web.ps1:73 — "--dart-define=WEB_PUSH_VAPID_PUBLIC_KEY=$VapidPublicKey"
    // docker-compose.prod.yml:54 — backend key is :?required from ~/fireplace/.env
- impact: The backend requires its own `WEB_PUSH_VAPID_PUBLIC_KEY` (docker-compose.prod.yml:54). If a web build omits the define, or `$VapidPublicKey` in the deploy config is empty, the frontend silently subscribes against either this baked-in key (likely not matching the backend keypair) or an empty key. Either way the browser creates a subscription that looks valid but the backend cannot authenticate to the push service (VAPID mismatch → push rejected). Push is silently dead on the iOS PWA with no error surfaced to the user or build. The `TODO: Replace with your real VAPID key` comment shipping in release source is the smell. deploy-web.ps1:73 does wire the define (verified), so a correctly-configured prod build is fine — the gap is the absence of any fail-fast guard.
- fix: Drop the real-looking `defaultValue` to `''` and assert at startup on web (`assert(_vapidKey.isNotEmpty)` plus an early return + `E2eDiagLog.add` marker like the badge-support marker in `unread_badge_sync.dart:37`) so a misconfigured build is obvious instead of silently producing un-pushable subscriptions. Confirm `deploy-web.config` sets `$VapidPublicKey` to the same key as the backend `.env`.

### C7-02 Web push subscription is never re-created when lost/expired
- severity: Medium
- confidence: Medium
- dimension: RESILIENCE
- location: frontend/lib/services/web_push_bridge_web.dart:61-70 (and push_service.dart:202-215)
- evidence: |
    Future<Map<String, dynamic>?> registerExistingSubscription({...}) async {
      if (!isSupported || notificationPermission != 'granted') return null;
      final registration = await _registerServiceWorker();
      final subscription =
          await registration.pushManager.getSubscription().toDart;
      return _toPayload(subscription, userAgent);   // null if no subscription → caller no-ops
    }
    // contrast requestSubscriptionFromUserGesture:83-84
    //   subscription ??= await _subscribe(registration, vapidPublicKey);
- impact: On every socket-ready, `PushService._registerExistingWebSubscription` (push_service.dart:202-215) only re-registers an already-existing subscription. If the browser/push service has dropped the subscription (storage eviction, push-service rotation, or `expirationTime` lapse — which is captured in `_toPayload:140` but never acted on) while `Notification.permission` is still `granted`, `getSubscription()` returns null, `_toPayload` returns null, and the startup path silently does nothing. The user appears subscribed (permission granted, settings toggle on) but receives no pushes until they manually re-toggle. On the iOS PWA — the primary web-push platform this gate targets — there is no auto-heal.
- fix: In `registerExistingSubscription`, when permission is `granted` and `getSubscription()` returns null, attempt `_subscribe(registration, vapidPublicKey)` (the spec permits `pushManager.subscribe` without a fresh gesture once permission is granted), mirroring the `subscription ??= await _subscribe(...)` already used in `requestSubscriptionFromUserGesture:83-84`. Guard with try/catch so a gesture-required engine degrades to today's behavior.

### C7-03 Deep-link conversation id accepted without range/sanity validation
- severity: Low
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/utils/notify_conv_param_web.dart:6-10 (also pending_deep_link_web.dart:42-45)
- evidence: |
    int? consumeNotifyConvParam() {
      final raw = Uri.base.queryParameters['notify_conv'];
      if (raw == null) return null;
      return int.tryParse(raw);            // accepts -1, 0, 2147483647, etc.
    }
- impact: `?notify_conv=<id>` and the IndexedDB record are parsed with `int.tryParse` only — any integer (negative, zero, absurdly large) is forwarded to `onNavigateToConversation` → `requestNavigateToConversationFromNotification`. Harm is bounded (it is an `int`, so no injection/XSS), but a crafted/garbage value navigates to a non-existent conversation and lands the user on an empty/failing chat screen rather than being rejected up front. Both deep-link carriers share this.
- fix: Reject non-positive ids at the parse boundary (`final id = int.tryParse(raw); if (id == null || id <= 0) return null;`) in `consumeNotifyConvParam` and in `consumePendingNotificationDeepLink` (`pending_deep_link_web.dart:42-45`), so only plausible server-assigned ids drive navigation.

### C7-04 Badge cap constant duplicated across Dart and the SW with only a comment to keep in sync
- severity: Low
- confidence: High
- dimension: PWA / WEB
- location: frontend/lib/utils/app_badge_math.dart:1-4
- evidence: |
    /// **Keep in sync** with `APP_BADGE_MAX` in `frontend/web/web-push-sw.js`.
    const int kAppBadgeMaxDisplayCount = 19;
- impact: The page caps the badge at 19 (`unread_badge_sync.dart:66`, `notification_cleaner_web.dart:76`) while the SW push handler writes `payload.unreadTotal` capped at its own `APP_BADGE_MAX`. If the two constants drift, a push-set badge and an app-set badge disagree on the saturation number (e.g. push shows 99+, in-app read clears/re-asserts 19), with no compile-time link to catch it.
- fix: Treat one side as authoritative. Since the page already posts the capped value to the SW for `set-badge`, prefer having the SW echo/trust the page-supplied cap, or generate both constants from a single source at build. At minimum, add the reverse "keep in sync" comment in `web-push-sw.js` (SW review C8 owns that side).

### C7-05 Web notification-click listener captures the first handler permanently (static gate)
- severity: Info
- confidence: Medium
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/services/web_push_bridge_web.dart:163-202
- evidence: |
    static bool _clickListenerRegistered = false;
    void listenForNotificationClicks(void Function(int?) handler) {
      if (_clickListenerRegistered) return;   // 2nd call (re-login) is a no-op
      _clickListenerRegistered = true;
      ... addEventListener('message', closure-capturing-`handler`) ...
    }
    // android side (android_fcm_local_notifications.dart:28-33) instead uses a
    // MUTABLE setter "updated each login so logout does not keep stale closures".
- impact: After logout the provider resets `_pushInitialized = false` (connection_provider.dart:284) and re-calls `initialize` on the next login, but the web bridge's static gate makes the second `listenForNotificationClicks` a no-op — the message listener keeps the first session's `handler` closure. In practice this is benign today because that closure routes through the singleton `ConnectionProvider` instance (created once in `main.dart`'s `MultiProvider`), so the live `_conversationsProvider` is still reached. It becomes a real bug only if `PushService`/`ConnectionProvider` are ever recreated within one page load. Flagged as an inconsistency: the Android path already solved this with a mutable handler.
- fix: Mirror the Android pattern — store the handler in a mutable field updated on each `listenForNotificationClicks` call and have the (still once-registered) listener invoke the current field value, instead of capturing the first closure.
