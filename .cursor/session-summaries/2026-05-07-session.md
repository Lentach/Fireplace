## Bugs found and fixed in this session

### 1. `requiresStandalone` gate was too aggressive (blocked Comet/Chrome desktop)
**Symptom:** clicking Settings → "Enable push notifications" in Comet/Chrome desktop showed `Add to Home Screen first…` snackbar, even though Comet is Chromium and supports Web Push from a regular tab.

**Root cause:** `WebPushBridge.isStandalone()` in `frontend/lib/services/web_push_bridge_web.dart` was checking `(display-mode: standalone)` for **all** platforms. Only iOS Safari/WebKit actually requires Home-Screen install + standalone mode for Web Push; every other engine (Chrome / Edge / Firefox / Comet on desktop and Android) can subscribe from a regular secure-context tab. The gate was rejecting them all.

**Fix:** renamed to `isStandaloneOrNotRequired()` and now only enforces the standalone check on iOS WebKit. Detection: `iPhone|iPad|iPod` in lower-cased UA, plus the iPadOS-13+ "Mac UA + `navigator.maxTouchPoints > 1`" heuristic. On iOS, considered standalone when `(display-mode: standalone)` matches OR `navigator.standalone === true`.

Files: `web_push_bridge_web.dart`, `web_push_bridge_stub.dart`, `push_service.dart`, `CLAUDE.md`.

### 2. `dart:html` PushManager null typing crash on first subscribe
**Symptom:** even after the gate fix, snackbar said success but `POST /users/web-push-subscription` never fired. Console showed two red `Uncaught (in promise) DartError: TypeError: null: type 'Null' is not a subtype of type 'FutureOr<PushSubscription>'` from `js_util_patch.dart:573`. `Notification.permission` was `granted` but `pushManager.getSubscription()` in console returned nothing — i.e. permission was burnt without an actual subscription ever being created.

**Root cause:** `dart:html` declares `PushManager.getSubscription()` as `Future<PushSubscription>` (non-nullable), but the JS API legitimately resolves to `null` when no subscription exists. Awaiting that typed Future blew up Dart's runtime type check **before** reaching the `subscribe(...)` branch, so a fresh device could never create its first subscription.

**Fix:** all `PushManager` interactions now go through `dart:js_util`:
- `js_util.getProperty(registration, 'pushManager')` → raw JS handle.
- `js_util.callMethod(pushManager, 'getSubscription' / 'subscribe', ...)` returning a `Promise`.
- `js_util.promiseToFuture<dynamic>(...)` so the Future is `Future<dynamic>` (nullable safe).
- `_toPayload(...)` reads `endpoint` / `getKey('p256dh' | 'auth')` / `expirationTime` via `js_util.getProperty` / `callMethod` on the raw subscription object.

`subscribe` options are built via `js_util.jsify({ 'userVisibleOnly': true, 'applicationServerKey': Uint8List(...) })`. `Uint8List` passes through to JS as a `Uint8Array`, which the Web Push API accepts as `BufferSource`.

Same change covers `unsubscribe()` (calls subscription.unsubscribe via `js_util.callMethod`).

File: `web_push_bridge_web.dart`. Bug + fix documented in `CLAUDE.md`.

## Decisions agreed with the user (sticky)
1. Branch `feature/web-push-vapid-migration` **stays unmerged** until real-phone tests pass.
2. **Body text in `web-push-sw.js` stays English-only ("You have a new message") for now.** Localization + sender preview deferred to a separate PR (would require backend payload changes, must stay E2E-safe — never include plaintext message body).
3. **Foreground push duplicate is intentionally NOT suppressed in `web-push-sw.js`.** iOS Safari has a "silent push budget" that revokes permission after a few `push` events without `showNotification`, so unconditional show is the safer default. If duplicate becomes annoying after real-user testing, the planned mitigation is **server-side**: `PushNotificationsService.notify()` would consult `ChatPresenceService` for `userId → activeConversationId` and skip the push when user is live in that exact conversation. SW stays untouched (iOS-safe). This is **deferred** until we have real feedback.
