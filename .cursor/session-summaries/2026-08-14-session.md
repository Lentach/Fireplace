# Admin password reset for user 54 + logout-cause investigation (no code changed)

**Date:** 2026-08-14

## What was done

Owner asked for a password reset for `Ketokeczup#6087` (user id 54), then for the cause of the
logout that made him ask. **No code was changed this session.** One prod DB write, one read-only
backup extraction, and a long evidence chase that killed three of my own hypotheses.

**The reset.** There is no admin reset endpoint — `POST /users/reset-password` requires the old
password — so it was done in the DB mirroring `UsersService.resetPassword`: bcrypt cost 10 hash
generated inside the backend container, then ONE transaction `DELETE FROM refresh_tokens WHERE
user_id=54` → `UPDATE users SET password=<hash>, "passwordChangedAt"=now()`. Revoke-before-stamp
is the order the service enforces (a stolen refresh token must not mint a fresh access JWT in the
gap). Verified by `POST /auth/login` → 201, then my own test session was deleted and
`passwordChangedAt` re-stamped to invalidate the access JWT it minted. Temp password is
`<REDACTED>` — handed to the owner in chat only, to be changed by the user.

**Reconstructed timeline.** 05-13 account created, identity `BcNWM+S196eX`, Apple push endpoint
(`web.push.apple.com`). 07-25 12:27 last message he sent (and the last one sent TO him, already
`READ`). **08-03 15:27 he changed his own password** — that revokes every session by design —
and re-logged in at 15:50:59; prekeys replenished 15:51:01. **That Aug 3 password is the one he
forgot.** 08-10 07:11:31–33 a fully authenticated cold boot: session slid, `fetchMe` OK, socket
connected, key bundle + push subscription re-upserted. After that, nothing, ever.

**The 08-10 refresh row was recovered from backup** — the single most useful move. Decrypted
`chatdb-20260813T040001Z.dump.gpg` and extracted the table read-only
(`pg_restore --data-only -t refresh_tokens -f`, nothing restored into the live DB):
`created_at 2026-08-03 15:50:59`, `expires_at 2027-08-10 07:11:31` → last slide 08-10 07:11:31,
two seconds before the key-bundle write. **His session was valid until August 2027 and was alive
when I deleted it.**

## Findings

- **The server never logged him out.** No `[auth-session-end]`, no revocation, no expiry, and
  **zero `login failed`** audit lines — he never submitted a wrong password. The loss was
  client-side: `AuthGate` shows the auth screen only when storage holds no token.
- **He has not logged in since the reset** — three independent surfaces: 0 rows in
  `refresh_tokens` (every login INSERTs one), only my `login success` at 00:50 in the audit log,
  and `key_bundles.updatedAt` still `2026-08-10 07:11:33` (any connect re-upserts it).
- **Online logout is excluded.** `logout()` deletes the push subscription AND the refresh row
  server-side; `web_push_subscription` id 370 is still present.
- **Two branches remain, byte-identical from the server:** an **offline Logout tap** (both calls
  swallowed by `catch (_) {}`, keys intact) vs **origin storage eviction / site-data clear**
  (keys gone). **Key loss is NOT ruled out.**
- **Architectural, and the real answer to "users must stay logged in":** on web the tokens
  (`auth_token_store.dart:31` — secure storage is Android-only) and the whole Signal identity
  (`signal_stores.dart:26-31`) share ONE localStorage. Session loss and permanent history loss
  are one event, and there is no key backup by design. No iOS setting changes that.
- **Fleet session health, unwatched:** of 48 accounts with a session row, 20 slid in the last 7
  days and 23 have not slid in over 14. `refresh_tokens.expires_at` is a per-device daily
  heartbeat by design (`auth_provider.dart:297-306`) and **nothing alerts on it** — this incident
  arrived as a support message instead.

## Three hypotheses I had to retract (do not resurrect them)

1. **"His history is intact."** Wrong. Identity churn is only observable when the client connects
   and re-uploads, and he has not connected since 08-10 07:11:33. The clean server record proves
   keys were alive UP TO 08-10 and says nothing about the window when the tokens vanished.
2. **Quota/partial-write loss of the refresh token.** Mechanically impossible: `/auth/refresh`
   echoes back the SAME opaque string (`auth.service.ts:95`, no-rotation by design at
   `refresh-tokens.service.ts:51-55`), so a swallowed `setString` rewrites a byte-identical value.
   Only a `remove` or an origin-level wipe can lose it.
3. **The auth screen's reason line as a wipe test.** `_lastSessionEndReason` is in-memory only
   (`auth_provider.dart:35`, set at `:169`, never persisted, never restored), so it reads bare
   after ANY cold boot under BOTH branches. I cited it three times before catching that; as a
   test it manufactures a false key-loss verdict.

Also note the 7-day WebKit cap does not fit: storage demonstrably held the refresh token across
08-03 15:50 → 08-10 07:11, and `web.push.apple.com` proves only "an Apple browser" (macOS Safari
16.1+ pushes to non-installed sites too), not a home-screen install.
