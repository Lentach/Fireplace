## E2E and local storage invariants

- Web Signal keys use `SharedPreferencesAsync`/localStorage only (`sig_` prefix) with one-time migration from legacy cached `SharedPreferences` namespace. Mobile uses `flutter_secure_storage`. Firebase on native initializes with NO Dart-side options (`Firebase.initializeApp()` — native default app from `google-services.json`); `firebase_options.dart`/`firebase_secrets.dart` were deleted 2026-07-29 because their placeholder values silently killed push on clean-checkout APKs.
- `EncryptionService` has an obsolete comment in `clearAllKeys` claiming `DualStorage.readAll()` merges both storages — it is platform-branched (web KV store OR secure storage, never both). Do not copy it; `signal_stores.dart` is the source of truth.
- Keys persist through logout. They are cleared only by account deletion (`clearEncryptionKeys()`), browser/site data deletion, or the §5.1 link ceremony disposing PROVEN-stale material (amendments (lxv)/(lxvii)). Multi-device is LIVE since 0.2.0 (2026-09-02): a second install gets the identity by LINKING from the primary (`docs/design/multi-device.md` §5.1), never by regenerating. Since D26 (0.2.23, (lxxviii)) the recovery phrase IS a key backup: the 12 words restore the same identity in seconds at the gate's restore door; they also shorten the §6.2 reset (6 h → 1 h since (lxxxii)) and, since (lxxxii) clause 2, reset the account PASSWORD alone (`AuthProvider.recoverPassword`, the "Nie pamiętam hasła" door). Local plaintext history is never in the backup.
- **The phrase is offered at the door and nudged on Czaty (spec (lxxxiii), 0.2.34; clause 4 in 0.2.35).** `AuthProvider.consumeFreshRegistration()` is stamped only on the two `register` paths that end signed in with an account these credentials CREATED (never the taken-but-mine path — an existing account may already hold a phrase); `ConversationsScreen` consumes it once and pushes `RecoveryKeyScreen(deferrable: true)` the moment `ownKeyBundleStatus` says **`hasRecoveryPhrase: false`** — never on unknown, never on true. Any account with an explicit `false` gets `BackupNudgeLine` above the list (`shouldShowBackupNudge` in `utils/backup_nudge.dart`; snooze = `SettingsProvider.snoozeBackupNudge`, prefs `backup_nudge_dismissed_at_<uid>`, 7 days; "Później" and the X both write it; a saved backup removes it via `onRecoveryKeySet`). **Not `hasIdentityBackup`** — 0.2.34 keyed off that and nagged the two prod users whose pre-0.2.23 phrase has a verifier and no blob (`goonboy`, id 48, saw twelve NEW words with no hint they would replace his paper); that flag drives only the devices screen's enrolled-primary nudge. The screen says `recoveryKeyReplacesExisting` above the generate button whenever `hasRecoveryPhrase == true`. Both flags reset to `null` in `clearAll()` (process singleton across logins). The generate button is gated on `isE2EReady` — `exportIdentityForBackup` throws before `initialize()` ran, and at the door the identity is minted seconds after the shell appears. The phrase does NOT lock the account: `setRecoveryKey` has no enrolment precondition; only "Włącz łączenie" enrols.
- **The link scanner is its own full-screen route (`LinkScanScreen`, 0.2.36; owner: the 280 px inline tile "looks like 2005").** Both ceremony screens push it (`fullscreenDialog: true`) and act on the popped `LinkScanResult` — `LinkScanCode` / `LinkScanUnsupported` / `LinkScanManual` / null (X). It pops exactly ONCE (the native `errorBuilder` can fire "unsupported" from the build phase, so every exit is a post-frame pop behind a latch). Camera fills the viewport (`Stack(fit: expand)`; the web `<video>` is `object-fit: cover`); the scrim with the square window is an `IgnorePointer(CustomPaint)` so it never sits between a pointer and the platform view; the X and the bottom controls are `PointerInterceptor` children (§7). No torch: the three-impl facade has no seam for it and it cannot be driven from this box. **Drive trap:** an OCCLUDED app-mode Chrome window reports `visibilityState: hidden`, Flutter stops ticking and a CDP screenshot catches the page transition frozen mid-way (the previous route bleeding through a scaled scanner) — bring the window to the front before judging a frame; `page.bringToFront()` does not un-occlude at the OS level.
- **The muted peer key-change line lives until the next message (spec (lxxxiv), 0.2.37; owner pick "a").** `peerKeyChangeNotes[peerId]` (ISO instant, `e2e_<uid>_peer_key_change_notes_v1`) renders in `ChatDetailScreen` only while nothing newer exists — `_isNewestInTimeline` checks `messages.last.createdAt` AND the conversations list's `lastMessages[convId]` (populated before history loads; without it the first paint after a reload flashes the evicted line). The first build that finds it superseded calls `EncryptionProvider.dismissPeerKeyChangeNote` (remove + persist + notify), once per instant (`_dismissedNoteAt`), so cleared history cannot bring it back. Two riders in the same amendment: (1) `EncryptionService.initialize(userId)` clears `_peersWithChangedIdentity` / `_peerKeyChangeNotes` / `_peersRefusedIdentity` / `_pendingSessionRebuilds` / `_deviceListPins` ONLY when the user id differs from the last one — the singleton survives logout and the loaders `addAll`, so account A's notes, pills and rollback pins used to apply to account B; a same-user re-init (passcode re-lock) keeps the unpersisted refusals. (2) `recordPeerIdentityChangedFromServer` no longer returns early on a repeat peer with warnings OFF — the muted ack has nothing staged, the peer stays in the standing set, and every later "new device" event for that peer was dropped (the line fired once per peer, ever). Tests: `chat_detail_identity_row_test.dart` (F46/F46b), `encryption_key_change_demotion_test.dart` (F47/F47b/F48).
- Plaintext decrypted-message cache is separate from Signal keys. The Privacy & Safety “Clear downloaded audio cache” button was REMOVED (2026-08-15, owner decision) — `PlaybackController.clearAudioCache` itself stays and still runs as part of “Delete all messages stored on this device” (`_deleteAllLocalHistory`). On web it is a no-op (`kIsWeb → return 0`); on native it deletes only `documents/audio_cache/`. It does NOT touch Signal keys, sessions, decrypted history, media keys, or pending-send plaintext.
- E2E envelope media keys are one-shot: once a media envelope is decrypted, persisted decrypted content is the surviving copy of `mediaKey`/`mediaIv`. Never overwrite an existing keyed media cache entry with keyless `[Decryption failed]` data.
- Live decrypt is serialized per sender. Do not live-decrypt outside the active conversation; Signal ratchet order matters. `[Decryption failed]` is terminal. Inbound decrypt failure must never delete the session record.
- `EncryptionService` serializes ALL per-peer Signal session mutations — `encrypt`, `decrypt`, `buildSession`, `deleteSession` — on ONE tail-chained queue per peer (`_sessionTails`). Two lessons paid for in the field: (1) concurrent encrypts emit DUPLICATE chain counters (2026-07-07 note burst); (2) an encrypt racing a DECRYPT loses one side's store — the decrypt's stale write-back rolls the sender chain back, the next encrypt reuses a counter, and the receiver permanently rejects a brand-new message (the post-0.0.90 fleet `[Decryption failed]` reports; `DuplicateMessageException 'old counter'`). Regressions: `test/services/encryption_send_race_probe_test.dart`, `test/services/encryption_encrypt_decrypt_race_probe_test.dart` (gated deterministic lost-update via `debugWrapSessionStore`). Never bypass these methods with a raw `SessionCipher`/`SessionBuilder`, and keep them LEAF-LEVEL: a guarded method awaiting another guarded method for the same peer chains behind itself and hangs.
- `_pendingSendContent` stores tempId → plaintext/media metadata; write `mediaKey`/`mediaIv` immediately after encryption and before any await.
- Lost-ack insurance (0.0.102): at `SEND_EMIT`, `_encryptAndSend` snapshots the `_pendingSendContent[tempId]` payload into a durable pending-send record keyed by the EXACT emitted ciphertext on a legacy send and by the per-tempId `sendToken` on a fan-out send (amendment (ix): a fan-out row carries no ciphertext for its own origin device) — ONE SharedPreferences key per record (`e2e_${uid}_pendsend_v1_<ct|token>`), NEVER a shared JSON blob (concurrent-save RMW = the `_sessionTails` lost-update shape). The `messageSent` ack consumes it; a lost ack is reconciled on the history-decrypt own-message branch via peek → persist under real id → VERIFY by read-back → take (`saveDecryptedContent` swallows failures — never consume-first, the record is the only surviving plaintext copy; a Signal sender cannot decrypt its own ciphertext). Match by exact record-key equality ONLY (`encryptedContent ?? sendToken`) — heuristic (timestamp) matching was review-rejected: a wrong match persists the WRONG plaintext permanently. TTL 72h/cap 40; wiped by `clearAllKeys` + `clearDecryptedContentCache`; deliberately NOT cleared on reconnect (the lost-ack case IS a reconnect). Diag: `SEND_ACK_RECONCILED` (durable).
- Media send path uses `EncryptedMediaUploadService`; its `onEncrypted(key, iv)` fires before upload await so callers can preserve keys. Retry reuses existing `mediaUrl`/`mediaKey`/`mediaIv` when upload already succeeded.
- Temporary diagnostics still exist: `E2eDiagLog` ring buffer (200, in-memory), the durable failure log `E2ePersistentDiag` (`e2e_diag_persist_v1`, capped 80, SharedPreferences — mirrors failure-class events `DECRYPT_DECISION`/`SEND_FAIL`/`SESSION_RESET`/`ENCRYPT_OVERLAP` so they survive ring eviction AND restart; `init()` in `main.dart` before `runApp`; both shown/copied/cleared in the Privacy & Safety hacker-mode panel), mic re-prompt log, storage durability probes. `DECRYPT_START` carries `ctype` (3 = PreKey/rebuild, 2 = whisper). Keep them until the underlying field issue is closed.
- `[Decryption failed]` reported in the field → follow `docs/runbooks/e2e-decryption-failed.md` FIRST (stale-build check → E2ePersistentDiag dump → signature table discriminating race-back / lock-deadlock / pre-fix damage / identity regeneration). Do not re-derive the diagnosis from scratch.
- **The plaintext-cache reload is COHERENCE, not decoration — hoist it, never delete it.** `getDecryptedContent` calls `prefs.reload()` on web before every read (`fd89e7e`) so plaintext another PWA engine wrote is visible; a stale snapshot = cache miss = live decrypt of a consumed ciphertext = real `DuplicateMessage`. But on web `reload()` is `getAll()`: enumerate EVERY localStorage key, then `getItem` + `jsonDecode` each `flutter.`-prefixed one, against a cache capped at 2000 records (~1.6-2.0 ms each, measured). The history pass called it once PER ROW — 65-77 ms of blocked main thread for one 50-row page, ~590 ms at 400 rows, 4-6x worse on a phone. Use `getDecryptedContentMany` (ONE reload per pass); anything landing mid-pass is still covered by the raw replay cache, which keeps its own reload. **A batch MISS is not an answer** — it reads SharedPreferences only, so callers MUST fall through to `getDecryptedContent` (the mobile legacy store lives only there); treating an absent id as "no plaintext" strands the row on `[encrypted]`. Cost probe: `tool/prefs_reload_cost_probe.dart`; runbook Step 3D.
- **Hydrate the history snapshot BEFORE the first paint, and never from RAM for OWN rows.** Every E2E row arrives as `content: "[encrypted]"`, so merging + notifying first made a long chat flash placeholders on entry. `_hydrateSnapshotFromCaches` fills the caller-local list first (upgrade-only; it can never downgrade a row). Own rows are deliberately excluded from the RAM half: the pass's own-message branch IS the lost-ack reconcile, and satisfying such a row from RAM flips its content, skips the branch, and the durable persist under the real id silently never happens (`messaging_provider_lost_ack_test.dart` catches exactly this). The disk half still hydrates own rows — a persisted entry means the reconcile had nothing left to do. The hydration is the ONLY suspension point before the merge, so `onMessageHistory` snapshots `_isPaginationLoad`/`_paginationConversationId`/`_historyFetchSeq` and drops a payload superseded under it (into the conversation cache, never discarded).
- **The identity is ONE atomic record, and a partial identity NEVER regenerates on its own.** `identity_key_pair` + `registration_id` used to be two independent keys: losing exactly one made `loadFromStorage()` report a fresh install, `_generateKeys()` minted a new identity, and every peer's history became permanently undecryptable — silently. Now `identity_record_v1` holds both in one write (legacy keys still read as a fallback and mirrored for older bundles; the migration is additive and never regenerates). `loadFromStorage` returns `loaded` / `absent` / `partial`; anything but `loaded` — including "no identity but sessions/prekeys survive" — is decided by the SERVER, never offline (multi-device amendment (lxxi)): `checkServerIdentity` answers for the login's device (a `ServerIdentityGuard {exists, linkingEnabled}` pair since (lxxiii); an absent `linkingEnabled` in `ownKeyBundleStatus` reads as `true` — fail closed against an older server). `exists && linkingEnabled` → `E2eIdentityIncompleteException`, storage untouched, and since (lxxiii) clause 3 the `DeviceLinkGateScreen` (mounted by `AuthGate` ABOVE the Offstage `MainShell`) offers the §5.1 link, the §6.2 reset door and the (lxxviii) phrase restore (`LinkRestoreSection`) — but never a "start fresh" (it minted an identity no peer trusts and flipped `_e2eInitialized` before the lock refused the upload). UNKNOWN → `E2eIdentityCheckUnavailableException`, retried next connect (flagged as `EncryptionProvider.identityCheckUnavailable` so the gate shows checking+retry, never a keyless shell). `exists && !linkingEnabled` (account never enrolled a DAK — the server accepts an 'unlocked' replacement) → residue discarded PROVEN, fresh identity minted, diag `IDENTITY_GUARD_UNLOCKED_REMINT`. `exists: false` → residue is discarded via `_wipeSignalMaterial` (`IDENTITY_RESIDUE_DISCARDED`) and a fresh identity minted without asking — a never-published identity protects nothing; but the discard must be PROVEN: a failing enumeration OR a row that would not delete records `IDENTITY_RESIDUE_DISCARD_DEFERRED` and defers like UNKNOWN, never mints over rows it could not see. A THROWING read still propagates — a storage error must never read as "no keys". The residue probe FAILS CLOSED when `readAll` itself fails (retry once, then `IDENTITY_RESIDUE_UNKNOWN` = residue-present): an enumeration transient must not wave `_generateKeys()` through over sealed sessions. Regressions: `test/services/encryption_identity_guard_test.dart`, `test/widgets/identity_banners_test.dart`.
- **A peer identity change is accepted but NO LONGER SILENT.** `isTrustedIdentity` is still TOFU (the message keeps flowing), but it now compares against the stored key and fires `onIdentityChanged` → persisted `PEER_IDENTITY_CHANGED` diag + `EncryptionProvider.peersWithChangedIdentity` state. The OLD full-width in-chat `PeerIdentityChangedBanner` was REMOVED by owner ruling 2026-08-15 (pushback recorded, overruled), but Phase 0a re-introduced a NARROWER in-chat surface on this branch (`6554fe7`, 2026-08-17), so the "banner is gone" reading of that ruling is now wrong: `PeerIdentityChangedRow` is a centered system pill on the error palette at the newest end of the timeline, rendered from TWO sites (`chat_detail_screen.dart:744` empty branch, `:811` populated branch), tapping it opens the fingerprint dialog. It must be rendered on BOTH the populated and the EMPTY branch of `_buildMessagesArea` — it used to live only inside the non-empty `ListView.builder`, so a cleared, expired or never-used chat showed nothing while the persisted alarm was live and the server `peerIdentityChanged` event needs no local message to raise it (fixed 2026-08-29, regression `test/screens/chat_detail_identity_row_test.dart`). The second surface is the "Verify security keys" door on the user card (`user_card_screen.dart` → `showPeerIdentityFingerprintDialog`), which also clears the standing warning via `acknowledgePeerIdentity`. A key change is usually a reinstall and is also exactly what a server inserting itself looks like; only the user can tell those apart. Two performance traps paid at the same time: libsignal calls this on EVERY encrypt and decrypt, so the store keeps a write-through memo (`_trustedMemo`) — on web one storage read enumerates the whole localStorage keyspace — and the write is now SKIPPED when the key is unchanged, making steady state cheaper than the unconditional write it replaced.
- **One-time prekey generation is origin-locked** (`fireplace-e2e-prekeys-<uid>`, its own name — it touches no SessionRecord, so it must NOT reuse the per-peer session lock). It is a read-modify-write of `next_pre_key_id` shared across PWA engines; unserialized, two tabs both minted ids 20..119 with different private halves and both uploaded, leaving the server serving a public prekey whose private half was overwritten → bad MAC for whoever drew it. Regression `test/services/encryption_prekey_race_probe_test.dart` includes a FALSIFICATION case asserting the unserialized version still collides.
- **A cold chat entry shows "Decrypting…", never the raw `[encrypted]` sentinel.** First entry has no cached plaintext, so every row must be Signal-decrypted before it can show anything — that is unavoidable STATE, and on a full page it takes SECONDS (device-observed: "every message was encrypted for 3-5 seconds, then turned into text"; instrumented in a debug web build at first row 4.7 s / pass 6.3 s for 50 rows). Rendering the sentinel for that window made a normal wait look like a failure. `TextMessageContent.decryptInProgress` (fed by `MessageContentFactory` via `MessagingProvider.isDecryptingHistory`) relabels ONLY rows matching `displayAsEncryptedPlaceholder` — so `[Decryption failed]` stays terminal, already-decrypted text is untouched, and keyed media never reaches this path at all (it renders through the media widgets). When the pass ends the flag clears and any still-unresolved row falls back to the real sentinel, so the label can never become a spinner over a permanent error. `retryDecryptActiveConversation` wraps the pass in try/finally for exactly that reason — a throw there used to strand the flag true for the session. Regressions: `test/widgets/message/decrypting_label_test.dart`.
- **Do NOT "reveal progressively" during the history decrypt pass.** The pass MUST run oldest-first (Double Ratchet ordering) while the list is `reverse: true` and shows the NEWEST rows, so mid-pass notifies resolve off-screen rows first and leave the visible ones on the placeholder until last — pure rebuild churn for no perceived gain. Tried and reverted 2026-07-28.
- **Plaintext the server no longer serves is destroyed by ASKING the server, never by inferring absence.** `EncryptionProvider.reconcileStoredPlaintext` snapshots every stored id (`storedMessageIds`, both id-keyed prefixes, no metadata read), asks `getServedMessageIds` in batches of 500, and purges what comes back missing. This is the only rule that reaches records written before the `_cid`/`_savedAt` stamps existed — they match no local rule and their server row is already gone. Four properties are load-bearing and each has a test that goes red without it: a null answer (timeout / dropped socket / any unparseable element) purges NOTHING while an empty list purges everything; the id set is snapshotted BEFORE the first request so a message arriving mid-pass is never in a batch; the purge is skipped if `activeUserId` changed mid-pass; and only a pass that heard back about every batch writes the 6-hour throttle stamp. **Never re-derive this from a history PAGE** — a page holds ~50 rows against a 2000-record store, so "not on this page" would read as "deleted" and destroy the archive of every long conversation.
- **All of `EncryptionService`'s at-rest content goes through the `ContentKv` seam, and the seam mirrors `SharedPreferences` EXACTLY** (`services/encryption/content_kv.dart`): synchronous `getString/getInt/containsKey/getKeys`, commit-gated `Future<bool>` writes, web-only `reload()`. That shape is deliberate — it made the native swap type-level, so every 0.0.135/0.0.136 purge, reconcile and sweep semantic above the seam is byte-identical on every platform. `PrefsContentKv` IS the historical behavior; the platform opener (`content_kv_opener_stub.dart` / `_io.dart`, conditional import) returns it on desktop and the flutter_test VM only — Android opens `NativeContentStore`, web opens the sealed `SealedWebContentKv` (canary-unblocked 2026-08-03), and each falls back to `PrefsContentKv` on failure. **Desktop and the flutter_test VM are unchanged by construction.** The NATIVE opener memoizes ONLY the Android path (the web opener memoizes its one sealed store): a process-wide memo pinned the first widget test's mock prefs and broke unrelated provider tests.
- **On Android the content store is an encrypted SQLCipher database, never a plaintext XML** (`native_content_store.dart` + `content_db.dart`, drift; file `<app support>/fp_content.db`, committed codegen `content_db.g.dart`). `DriftRecordDb.open` passes the raw key as `PRAGMA key="x'<hex>'"` and then **throws unless `PRAGMA cipher_version` answers non-empty** — a plain `sqlite3` binary silently ignores `key` and would give you a store that looks sealed and is not. `secure_delete=ON`, WAL. Three key families are AES-GCM sealed per row (`12B IV || ct` in the value column, key id in a cleartext `kid` column): `_decrypted_`, `_decrypt_raw_v1_`, `_pendsend_v1_`. Control records (retired set, purge backlog, retention epoch, reconcile marks) stay CLEARTEXT inside the encrypted DB on purpose, so they survive content-key loss and can still describe what was lost.
- **Two keys, different jobs, both Keystore-backed** (`content_key_manager.dart`, same `FlutterSecureStorage` instance as the Signal keys, no auth binding): the DB key `fp_content_db_key_v1` is static and NEVER rotated (rotating it would re-encrypt pages, not shred them; losing it means secure storage died, which already killed the Signal identity), and content keys `fp_content_key_<kid>` rotate. They live OUTSIDE the `e2e_<uid>_` namespace so `clearAllKeys` cannot sweep them. Every key is **armed** before use — write, then read back in a fresh call, and only then seal with it.
- **Key loss must be PROVEN, never inferred.** `inventory()` returns null when enumeration itself fails, and null means change NOTHING: a transient Keystore failure that read as "keys gone" would retire the user's whole history. Only a successful enumeration that is missing a specific `kid` retires that kid's rows, at open, BEFORE any decrypt attempt (ids parsed out of the row keys and folded into `e2e_<uid>_retired_v1`, cap 5000, same shape as `markRetired`). **Retired rows are never deleted** — the key may come back. Diags: `CONTENT_KEY_LOST`, `CONTENT_RECORDS_UNREADABLE`.
- **Shredding is key rotation, not deletion, and it is batched by design.** A `remove()` of a sealed key gates on BOTH the DB delete and the legacy-prefs remove, then bumps the durable `shred_gen` meta int and schedules a rotation (20 s debounce, 3 min hard deadline, `rotateNow()` public, fired from `main_shell.dart`'s background hook). Rotation mints and arms a new kid, re-seals every retiring row in all-or-nothing 64-row batches, re-seals the audio cache, and only THEN destroys the old keys; any failure calls `_retryLater(stage)` + `ROTATION_RETRY` and keys survive. `shred_done_gen` defaults to **0** when absent, not to `shred_gen` — defaulting to gen silently lost the obligation across a restart. Owner-facing contract: "removed instantly, shredded within minutes."
- **Nothing is destroyed until it is PROVEN nothing live still needs the key** — three gates, all added after a review found two permanent-loss paths, each with a fail-before test in `native_content_store_test.dart`: (1) a sealed write captures its kid AND its key bytes together before the seal await, because a rotation flipping `_activeKid` mid-seal used to label the row with a key that never encrypted it — and the reseal pass finds rows BY kid, so a mislabelled row was invisible to it and died with its real key; (2) rotation waits for in-flight sealed writes (`_sealedWritesIdle`, 10 s cap → `_retryLater('quiesce')`) and then re-checks `rowsByKid` for every retiring kid, deferring the shred (`late-rows`) rather than destroying a row that landed after the reseal pass; (3) a refused unseal is AMBIGUOUS, so before treating it as corruption the cipher must round-trip a probe under the same key (`_cipherHealthy`) — a webcrypto failure under memory pressure (rotation runs from the background hook, exactly when the OS reclaims) defers with `ROTATION_RETRY{cipher}` instead of destroying rows that read fine at open. Provably corrupt rows are retired (`ROTATION_SKIPPED_ROWS`) so they render "no longer stored" in the same session, and they never block the shred.
- **The store is main-isolate only.** The FCM background isolate (`android_fcm_local_notifications.dart:36`) inits Firebase + the notification plugin and nothing else — it must never be handed a `ContentKv`. `reload()` is a no-op precisely because one process/one isolate owns the view; a second opener would fork the RAM view and let two rotations race the same keys.
- **The fallback is prefs, loudly — never an unencrypted DB.** Any open failure throws `ContentStoreUnavailable(stage)`; the opener catches it, returns `PrefsContentKv`, and records `CONTENT_STORE_FALLBACK{stage}` (`web-<stage>` on web). The ONE exception is the web `locked` case (passcode vault locked): it rethrows and records `CONTENT_STORE_LOCKED`, because falling back there would write the plaintext cache while the app is still locked. Status quo plaintext with a diag beats a store that pretends to be sealed.
- **Legacy prefs are drained, not abandoned:** existing `e2e_*` values are seeded into the store's RAM view at open (DB wins on conflict), then removed from prefs in commit-gated batches of 32, resumable by construction. `E2ePersistentDiag.storageKey` is excluded BY REFERENCE — it is a StringList the drain cannot carry, and draining it would have deleted the diag history every launch. Only String/int values are ever claimed.
- **Voice notes are sealed on disk too** (`sealed_audio_codec.dart`: `FPAE` envelope `magic|ver|kidLen|kid|IV12|GCM-ct`). Cache hits peek 5 magic bytes: legacy plain files keep the zero-copy `setFilePath` path, sealed files are unsealed to RAM and played via `setAudioBytes`. **That RAM path needs the loopback network security config** — just_audio serves in-memory sources over a `127.0.0.1` proxy and API 28+ blocks cleartext; without `android/app/src/main/res/xml/network_security_config.xml` sealed voice notes fail to play in RELEASE only. Rotation re-seals the cache (`audio_reseal.dart`, tmp+rename) BEFORE the old key is destroyed.
- **The JWT is Keystore-backed on Android only** (`services/auth_token_store.dart`; `!kIsWeb && Platform.isAndroid`, constructor override for tests). One-time migration copies from prefs, verifies by read-back, then deletes the prefs copy; a failed write leaves prefs as the working set; `clear()` sweeps both. Every pre-existing auth test still runs the prefs path unchanged.
- **Dependency pins that are load-bearing:** `drift >=2.31.0 <2.32.0` (and `drift_dev` to match) + `sqlite3 >=2.9.0 <3.0.0` + `sqlcipher_flutter_libs ^0.6.8` — the upper bounds are EXPLICIT because `^2.31.0` would have let the next `pub upgrade` pull the very version the note forbids. Deliberately NOT sqlite3 3.x/drift ≥2.32 — those use native-assets build hooks that demand MSVC on EVERY local `flutter test` (the exact trap `webcrypto` 0.6.1 set, which is why webcrypto stays pinned at 0.6.0). `sqlcipher_flutter_libs` being EOL is acceptable: it only bundles `.so`s, and the real guarantee is the empirical 16KB gate on the built APK.
- **The store is at-rest protection, not an offline cache.** The chat list is socket-driven, so a cold start with no network shows skeletons and no conversations (verified on the emulator 2026-07-29); what the store guarantees is that a message decrypted once still renders after a process restart, because the persisted plaintext record is the only surviving copy of a consumed ratchet message.
