# PWA logout incident — investigation (no code changes)

**Date:** 2026-07-24 — Auth incident root-caused: server-side auth infrastructure confirmed healthy; the one owner-verified victim was proven (via Postgres xmin forensics) to have suffered a FULL on-device origin-storage wipe — tokens AND Signal identity destroyed, identity regenerated on re-login.

## What was done
1. Verified server-side auth stack end to end on the prod VM (read-only): clock correct, backend 0.0.123/`4609af2` healthy, `JWT_SECRET` persisted in `~/fireplace/.env` (compose hard-fails without it; deploy never generates) — secret rotation/loss REFUTED.
2. `/auth/refresh` (sliding 365-day sessions, backend since 2026-07-04, client since 0.0.47/2026-06-10) is deployed and **100% successful: 112/112 requests returned 201 over the full 14-day nginx window; zero 4xx/5xx; zero `[auth-session-end]` rejections in backend logs**. Most active users hold one healthy sliding session.
3. "Logged out after 1 day+" = the 24h access-JWT TTL firing on devices that never present a refresh token at all. DB fingerprint: affected devices' refresh rows sit at exactly `created_at`+365d (never slid once). Eliminated noise: top churner = owner's incognito build checks; one "victim" was a new registration; another an explicit account switch.
4. **Owner-verified victim root-caused with proof.** Victim reported logout at 20:56 local 07-23; DB shows the matching re-login to the second. Their previous session HAD been sliding (last refresh 07-22 14:47 — current bundle, working refresh). At the next open (07-23 18:55) nginx shows a full cold bundle fetch and a straight login with no refresh attempt and no /auth/logout. Forensics: their 20 one_time_pre_keys rows + key_bundles row all carry xmin from the 07-23 evening range (17545–17846 vs 16363 for their own 07-20 login row) — the client re-uploaded a REGENERATED identity. Conclusion: the device's entire origin storage (Signal keys + tokens + Cache Storage/SW) was wiped between 07-22 14:47 and 07-23 18:55 by the browser/OS/user, not by app code (no app path clears sig_ keys; every reachable token-clear path leaves server traces that are absent). Old history on that device is permanently undecryptable; peers needed session rebuild. Forensic note: OTP upsert on (userId,keyId) preserves createdAt and overwrites identityPublicKey — timestamp/tag forensics mislead; use xmin.
5. Historical shape explained: pre-0.0.47 clients had no refresh at all (daily logout by design); 0.0.47→07-04 clients used single-use rotation which could strand clients on a lost response (matches heavy early-July churn clusters that stopped after the sliding fix).
6. RULE ZERO verified in source: `_clearLocalAuthState` removes only `jwt_token`/`refresh_token`; Signal keys survive logout and re-login reuses the on-device store when it exists. The app is key-safe; the DEVICE-level wipe is the data-loss vector.

## Platform verification (2026-07-24, sources checked)
- `navigator.storage.persist()`: Chrome/Android auto-grants for installed PWAs and granted origins are excluded from automatic eviction (MDN Storage quotas/eviction). REAL protection on Android — covers the one proven victim's platform.
- iOS/WebKit: home-screen install status itself exempts the app from the 7-day ITP purge (webkit.org storage policy; Wilander statement that first-party data in home-screen web apps should not be deleted). `persist()` grant behavior on iOS is undocumented/best-effort (MDN: browser may or may not honor). Do NOT claim iOS coverage from persist() alone.
