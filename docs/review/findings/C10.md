### C10-01 setState after await with no `mounted` guard in pinned-message jump
- severity: Medium
- confidence: High
- dimension: LIFECYCLE & LEAKS
- location: frontend/lib/screens/chat_detail_screen.dart:77-99
- evidence: |
    final listIndex = await loadListIndexForMessageId(
      messageId: messageId,
      ...
      loadOlderPage: () =>
          messaging.loadOlderMessages(widget.conversationId),
    );

    if (listIndex == null) {
      if (mounted) {                          // <- guarded
        showTopSnackBar(context, l10n.snackbarPinnedMessageUnavailable);
      }
      return;
    }

    setState(() {                             // <- NOT guarded by mounted
      _scrollTargetListIndex = listIndex;
      _scrollTargetKey = GlobalKey();
    });
- impact: `_scrollToMessageId` is invoked from the pinned-message banner tap (line 192). `loadListIndexForMessageId` awaits (it may page older messages over the socket). If the user pops the chat — common on iOS PWA where resume can also dispose the route — while that await is in flight and the message IS found (listIndex != null), the unguarded `setState` at line 96 runs after dispose and throws `setState() called after dispose()`. The null branch is correctly guarded (line 90), so only the success path is exposed. Tapping a pinned banner then quickly backing out crashes/red-screens that frame.
- fix: Add `if (!mounted) return;` immediately after the `await` (before line 96), mirroring the existing guards used at lines 90, 116, 129, 133 in this same method and the `if (!mounted) return;` pattern used throughout `initState`/`didUpdateWidget` postFrame callbacks.

### C10-02 Conversation/contact lists conflate "loading" with "empty" (misleading first-load state)
- severity: Medium
- confidence: High
- dimension: UX READINESS
- location: frontend/lib/screens/conversations_screen.dart:249-281 (same pattern: frontend/lib/screens/contacts_screen.dart:198-232)
- evidence: |
    Widget _buildConversationList() {
      final convs = context.watch<ConversationsProvider>();
      final conversations = convs.sortedConversations;
      ...
      if (conversations.isEmpty) {
        return Center(... AppLocalizations.of(context).noConversationsYet ...
                            AppLocalizations.of(context).startNewChatToBegin ...);
      }
- impact: There is no loading state — the only branch for a non-populated list is the "No conversations yet / Start a new chat to begin" empty copy. On every cold start/login (and on each socket (re)connect before `conversationsList` arrives) a returning user with many chats sees the empty-state flash until the server snapshot lands. The provider already exposes the signal needed to distinguish the two cases — `hasLoadedConversationsOnce` (conversations_provider.dart:91), which `MainShell` itself relies on for the notification-nav gate (main_shell.dart:151) — but neither list consults it. Affects both iOS PWA and Android. ContactsScreen has the identical gap (`friends.isEmpty` only).
- fix: Gate the empty copy on `convs.hasLoadedConversationsOnce` (and the friends-loaded equivalent), showing a spinner/skeleton until the first snapshot arrives — reuse the `CircularProgressIndicator` pattern already used in `add_or_invitations_screen.dart:213` and the pagination spinner in `chat_detail_screen.dart:643`.

### C10-03 Auto-send friend request has no idempotency flag + mutates state during build
- severity: Low
- confidence: Medium
- dimension: CORRECTNESS & STATE
- location: frontend/lib/screens/add_or_invitations_screen.dart:128-166
- evidence: |
    if (friends.consumeFriendRequestSent() && !_requestSent) {
      _requestSent = true;          // <- field mutation during build (no setState)
      _loading = false;             // <-
      ...
    }
    ...
    // Auto-send when exactly one result
    if (searchResults != null && searchResults.length == 1 && _loading) {
      WidgetsBinding.instance.addPostFrameCallback((_) {
        if (mounted) {
          final user = searchResults.first;
          context.read<FriendsProvider>().sendFriendRequest(user.id);
          context.read<FriendsProvider>().clearSearchResults();
        }
      });
    }
- impact: The auto-send is gated only on `_loading`, with no "already scheduled" flag (unlike `_loadingResetScheduled` used two blocks above at line 150). If the widget rebuilds again — e.g. `conn` (`ConnectionProvider`) or `convs` notifies — between the results-arrival build and the queued post-frame firing, while `_loading` is still true and `searchResults.length == 1`, a second `sendFriendRequest` post-frame is queued; both fire (each captures a non-null `searchResults` from its own build), producing a duplicate friend request. Window is narrow and likely absorbed by backend dedupe, but it is a real correctness smell. Separately, `_requestSent`/`_loading` are written directly inside `build()` (lines 129-130), violating build purity. Verified safe-from-throw: `consumeFriendRequestSent()` (friends_provider.dart:52-55) and `consumePendingOpen()` (conversations_provider.dart:113-117) do NOT call `notifyListeners`, so consuming them during build does not raise the "notify during build" assert.
- fix: Add a `_autoSendScheduled` guard mirroring `_loadingResetScheduled`, and move the `_requestSent`/`_loading` assignments out of `build()` into the post-frame callback (set via `setState`).

### C10-05 Fragile multi-consumer of `pendingOpen` across always-mounted ContactsScreen + Add tabs
- severity: Low
- confidence: Medium
- dimension: CORRECTNESS & STATE
- location: frontend/lib/screens/contacts_screen.dart:152-166 (vs frontend/lib/screens/add_or_invitations_screen.dart:121-126 and :283-292)
- evidence: |
    // contacts_screen.dart (comment claims Add "only consumes when that screen is open"):
    if (convs.pendingOpenConversationId != null) {
      WidgetsBinding.instance.addPostFrameCallback((_) {
        final id = context.read<ConversationsProvider>().consumePendingOpen();
        if (id != null && context.mounted) { Navigator.of(context).push(... ChatDetailScreen ...); }
      });
    }
    // add_or_invitations_screen.dart consumes SYNCHRONOUSLY in build:
    final pendingId = convs.consumePendingOpen();
    if (pendingId != null) { ...addPostFrameCallback(... Navigator.pop(pendingId)); }
- impact: `ContactsScreen` lives in `MainShell`'s `IndexedStack` (main_shell.dart:209-213), so it stays in the tree and rebuilds on every `ConversationsProvider` notify even when another route (the Add screen) is pushed on top. Three widgets consume the single `pendingOpen` token. The comment at contacts_screen.dart:154 ("AddOrInvitations only consumes when that screen is open") is inaccurate — Contacts consumes whenever built, i.e. always. It currently works only because the Add tab consumes synchronously in `build()` while Contacts defers to a post-frame, so within a shared notify frame the synchronous consumer wins and Contacts gets null. This is an undocumented ordering dependency; any refactor that makes Contacts' consume synchronous (or Add's deferred) would let Contacts steal the token and push `ChatDetailScreen` on top of the modal Add screen instead of popping it.
- fix: Centralize `pendingOpen` navigation in one owner (e.g. `MainShell`, which already owns `pendingNotificationConversationId` routing at main_shell.dart:150-171) rather than racing three screen builds; or document the sync-vs-postframe ordering contract explicitly at each consumer.

- impact: `_buildContactsList` sorts the friends list on every rebuild (`..sort(_compareByDisplayName)`, line 200-201), and the comparator constructs two fresh `RegExp` objects per invocation — O(n log n) regex compilations per rebuild. ### C10-09 1 Hz expiry/countdown Timer ticks unconditionally regardless of visibility
- severity: Low
- confidence: Medium
- dimension: PERFORMANCE
- location: frontend/lib/screens/conversations_screen.dart:34-43
- evidence: |
    _listCountdownTimer = Timer.periodic(const Duration(seconds: 1), (_) {
      if (!mounted) return;
      if (messaging.isRecordingVoice) return;
      messaging.removeExpiredMessages();
      context.read<ConversationsProvider>().pruneExpiredLastMessages();
      messaging.countdownTickNotifier.value++;
    });
- impact: `ConversationsScreen` is always mounted (IndexedStack), so this 1 Hz timer runs continuously and bumps `countdownTickNotifier` every second whether or not any ephemeral message is on screen and whether or not the tab is foregrounded. On web/PWA a backgrounded-but-not-suspended tab keeps ticking (rebuilding any countdown listeners + two provider scans per second). Correctly cancelled in `dispose()` (line 73) and correctly guarded by `mounted` — no leak — but it never pauses on background/visibility loss. Minor CPU/battery cost. (Centralizing the timer here to avoid duplicate timers when a chat is open is itself sound — see chat_detail_screen.dart:330-331 comment.)
- fix: Pause the timer when `setClientVisible(false)`/`AppLifecycleState.paused` (MainShell already tracks this, main_shell.dart:112-122) or skip the tick when there are no expiring messages, restarting on resume.

### C10-10 (Info) Notification-nav Option-A gate is correctly implemented
- severity: Info
- confidence: High
- dimension: CORRECTNESS & STATE
- location: frontend/lib/screens/main_shell.dart:143-172
- evidence: |
    if (convs.pendingNotificationConversationId != null &&

## Chunk summary
Six chat/shell screens reviewed in full plus cross-checked providers. Lifecycle hygiene is generally strong: ScrollController/Timer/observer/subscription disposal is correct in every screen, `mounted` guards are pervasive across post-frame and post-await callbacks, the iOS-resume dispose-churn is handled via `reassertOpenConversationOnResume`, and the notification-nav Option-A gate is correctly implemented (C10-10). No Blocker/High issues found. The one genuine crash path is an unguarded `setState` after an await in the pinned-message jump (C10-01, Medium); the most user-visible polish gap is loading-vs-empty conflation on cold start (C10-02, Medium). Remaining items are Low/Info: friend-request auto-send idempotency, missing multi-result picker, fragile `pendingOpen` multi-consumer, regex-in-comparator, an i18n string hack, a non-reactive block banner, and an always-on 1 Hz timer.
