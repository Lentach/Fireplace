### C9-01 copyWith cannot null-out any nullable field (no sentinel pattern)
- severity: Low
- confidence: High
- dimension: CORRECTNESS & STATE
- location: frontend/lib/models/message_model.dart:201-246
- evidence: |
    expiresAt: expiresAt ?? this.expiresAt,
    replyTo: replyTo ?? this.replyTo,
    mediaUrl: mediaUrl ?? this.mediaUrl,
    editedAt: editedAt ?? this.editedAt,
- impact: |
    The `x ?? this.x` idiom means passing `null` is indistinguishable from "leave unchanged", so no
    caller can CLEAR a nullable field via copyWith (expiresAt, replyTo, mediaUrl, linkPreview*,
    editedAt, mediaKey, mediaIv). Today this is masked because the merge logic
    (`_mergeMessagePreferNewer`) only ever upgrades toward non-null and edits are permanent, so
    nothing needs to reset a field. It is a latent foot-gun: a future "turn off disappearing on this
    row" or "remove link preview" reconciliation would silently no-op.
- fix: |
    If clearing a nullable field is ever needed, adopt the sentinel pattern (e.g. an `Object? expiresAt
    = _sentinel` parameter, set only when the caller explicitly passes it). Not required now — record
    the limitation. Reference: Flutter's freezed/`copyWith(... = const $sentinel)` convention.

### C9-02 Required numeric fields use bare `as int` while optional ones use defensive coercion
- severity: Low
- confidence: Medium
- dimension: CORRECTNESS & STATE
- location: frontend/lib/models/message_model.dart:123,125,127 ; conversation_model.dart:25 ; user_model.dart:18 ; friend_request_model.dart:22
- evidence: |
    id: json['id'] as int,
    senderId: json['senderId'] as int,
    conversationId: json['conversationId'] as int,
    // vs defensive elsewhere in the SAME factory:
    disappearAfterSeconds: (json['disappearAfterSeconds'] as num).toInt(),
    mediaDuration: (json['mediaDuration'] as num).round(),
- impact: |
    A non-int JSON shape for a required id (stringified id, or a JSON number Dart decodes as `double`
    — e.g. a value > 2^53, or a backend serializer change) throws `type 'String'/'double' is not a
    subtype of int` inside `fromJson`. Since history parsing maps a whole batch, one malformed row can
    throw and (depending on the caller's try/catch) drop a page of history. The current NestJS/TypeORM
    backend emits integer ids so this is low-likelihood, but the inconsistency removes the defense the
    optional fields have.
- impact_platform: both
- fix: |
    Use the same `(json['id'] as num).toInt()` coercion for required ids that the optional numeric
    fields already use, for uniform robustness against numeric-type drift.

### C9-03 createdAt/expiresAt stored as parsed (UTC) — display must convert
- severity: Info
- confidence: High
- dimension: CORRECTNESS & STATE
- location: frontend/lib/models/message_model.dart:128,130-132
- evidence: |
    createdAt: DateTime.parse(json['createdAt'] as String),
    expiresAt: json['expiresAt'] != null ? DateTime.parse(json['expiresAt'] as String) : null,
- impact: |
    `DateTime.parse` of a `...Z` ISO string yields a UTC `DateTime`; the model stores UTC (correct —
    store UTC, convert at the edge). Calendar-day/time rendering MUST call `.toLocal()` (frontend
    CLAUDE.md §1 chat-dates gotcha). This is a cross-cutting reminder for the widget chunks (C10/C12),
    not a model defect. No `==`/`hashCode` is defined, which is fine because messages are keyed by
    `int` id in caches/merges, not by value equality.
