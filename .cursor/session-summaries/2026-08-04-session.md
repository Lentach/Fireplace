# Backend security/reliability audit (read-only) + 4 cross-tier answers

**Date:** 2026-08-04

## What was done

Full read-only audit of the NestJS/Postgres tier (`backend/src`, 156 files / 109 non-spec /
10,128 lines, plus all 10 `migrations/*.sql`), run as 10 parallel `reviewer` subagents by slice
plus `chat.gateway.ts` reviewed directly. **No source file was modified.** Findings live ONLY in
`.planning/full-audit/backend/` (gitignored, `.gitignore:58`) — deliberately never committed:
it is a concentrated inventory of unfixed vulnerabilities in a live E2E messenger. This summary
is the only committed trace and names the findings without reproducing the exploit detail.

**52 findings: 0 CRITICAL, 4 HIGH, 20 MEDIUM, 27 LOW, 1 INFO.** Coverage 109/109 non-spec (100%).

**Verdict: the backend is well built.** The class that would be unrecoverable is **confirmed
absent** — no error handler advances or persists ratchet/session/prekey state on a failed
operation. OTP claim is atomically single-serve; the `repo.query()` `[rows,rowCount]` trap that
bit this repo twice is currently correct at every call site; secret-note reveal quotes
`"expiresAt"` correctly and only `POST /reveal` burns a note (no GET/HEAD/bot path can); SSRF
holds on both layers with the pinned-DNS agent as sole `fetchImpl`; the migration runner's
advisory lock releases on every throw and the two-container boot race is safe; all 13 entities
match their migrations; the 2026-08-03 hard-delete guard fails closed with exact
`string_to_array`/`ANY` matching (no comma-substring bug) and `detachReplies` runs in all three
paths.

### The 4 HIGH (detail in `.planning/full-audit/backend/FINDINGS.md`)

- **BE-301 + BE-300 — media cleanup can permanently delete live E2E blobs.** The 03:00 orphan
  cron snapshots disk+DB then unlinks; a row committed in that gap is deleted anyway, and grace
  is measured from file mtime, not row-insert time. **BE-300 makes it routine:** `resolveGraceMs`
  does `Number('')` → `0`, which passes the `isFinite && >= 0` check, so a *present-but-empty*
  `MEDIA_CLEANUP_GRACE_MS` silently sets the grace window to zero. Only a non-numeric/negative
  value falls back to the 15-min default. **This is the only finding that permanently destroys
  user data.** Fix BE-300 first — ~10 lines, de-risks BE-301.
- **BE-101 — blocking is incomplete, and the client does not compensate (CONFIRMED both tiers).**
  Block does not delete pending friend requests (`unfriend` removes only `ACCEPTED` rows),
  `getPendingRequests` has no block filter, `acceptRequest` has no block check. Frontend traced
  end-to-end: `friends_provider.dart:111-118` → `invitations_screen.dart:413-420` renders a live
  Accept for every request with no block filter at any hop; `blockUser()` drops nothing locally
  and `onBlockedList` prunes `_friends` only. So request → block → **Accept still works** →
  friends with a blocked user, and on unblock the friendship is already live with no fresh
  consent. Also: block leaves the conversation alive, and reactions/typing/voice check membership
  but never re-check block (BE-202), giving a blocked user a live interaction channel.
- **BE-250 — no unique constraint on the conversation pair.** `findOrCreate` is check-then-insert;
  concurrent starts create two rows for one pair. The catch-based race recovery is **dead code**
  (nothing raises 23505). ⚠️ The fix is a unique index, but if prod already holds duplicate pairs
  `CREATE UNIQUE INDEX` **aborts boot** — dedupe first, and no `CONCURRENTLY` inside a migration.
- **BE-004 — 8 WS events have no rate limit at all.** `APP_GUARD` is `HttpThrottlerGuard`, whose
  `canActivate` is `if (context.getType() !== 'http') return true` — a correct fix for the
  `res.header()` crash on sockets, but it means the global limiter is a no-op for WS and the
  `ThrottlerModule` 100/15min is only a default *value* for `WsThrottlerGuard`, not a fallback
  guard. Unguarded: `messageDelivered`, `markConversationRead`, `typing`, `recordingVoice`,
  `uploadKeyBundle`, `acceptFriendRequest`, `rejectFriendRequest`, `unblockUser`. Worst two:
  `markConversationRead` (unbounded writes + re-stamps disappearing-message expiry) and
  `uploadKeyBundle` (unbounded crypto-identity overwrite, while its neighbour
  `uploadOneTimePreKeys` is the tightest-limited event in the file — oversight, not decision).
  Independently rediscovered as BE-401 by the crypto slice. Fix = class-level guard so omission
  fails safe; **measure real rates first** — over-throttling `uploadKeyBundle` could block key
  republication, which is worse than the abuse.

### Notable MEDIUM

`deleteAccount` does destructive external I/O outside the transaction while a comment claims
otherwise → failure leaves a **zombie account that still logs in** with keys destroyed (BE-351).
`resetPassword` stamps `passwordChangedAt` *before* revoking refresh tokens → a stolen token can
mint a 24h JWT that survives the reset (BE-350). Unguarded `JSON.parse` in `message.mapper.ts:29`
on every emit path, beside a deliberately guarded parse in the service — one corrupt row can
blank a conversation (BE-153). Web Push deletes **live** subscriptions on an ambiguous HTTP 400,
so one payload/VAPID fault could mass-wipe the table (BE-500). Per-minute expiry cron has no
overlap guard and an unbounded `getMany()` (BE-150). Concurrent reactions clobber (BE-152/201).

### Cross-tier answers (4 questions that decided severities)

- **BE-001 — MIXED, stays live.** All list/message fetches correctly wait for `socketReady`
  (`connection_provider.dart:329-395`), and `sendMessage` is composer-initiated, so **there is no
  message-loss vector**. But `initializeE2E` runs from the raw `connect` handler (`:183`, `:262-303`)
  and emits `uploadKeyBundle`/`uploadOneTimePreKeys` (`encryption_provider.dart:847-861`) ungated
  — they can land in the pre-auth window and be silently dropped, leaving the server without a
  current key bundle so **new peers cannot open a session** until the next reconnect. Self-healing
  (re-uploads every connect); realistically only lost on fast reconnects.
- **BE-402 + BE-002 — DROPPED, both non-issues.** `onSessionRebuildNeeded`
  (`encryption_provider.dart:1012-1019`) only adds the id to a Set; it is consumed solely by
  `ensureSession` on the next *outbound send to that id*, which a stranger never triggers. And the
  rebuild **archives rather than deletes** — `ensureSession:147-160` carries an explicit comment
  that the old `deleteSession` "wiped current + all 40 archived states" and was removed. Listeners
  are registered before connect, so no pre-`socketReady` frame is missed.
- **Push suppression — HOLDS.** All four native lifecycle states route through
  `setClientVisible(false)` (`main_shell.dart:141-176`, `inactive` deliberately treated as
  background); web `visibilitychange` covered (`tab_visibility_web.dart:11-16`); reconnect
  re-asserts live state (`connection_provider.dart:285-286`, `551-552`); leaving a chat nulls the
  active id (`chat_detail_screen.dart:327`). One unverifiable desktop-web edge: alt-tab where the
  tab stays `visible` may keep suppressing that chat's banner (Flutter-version dependent).

### Incidental discovery — RESOLVED, suspicion was WRONG

`/messages/` is **not** proxied in `frontend/nginx.conf` — but **that file is the CONTAINER nginx
inside the frontend image, not the edge.** The host edge is
`/etc/nginx/sites-enabled/fireplace`, and it **does** proxy it (`:46-54`,
`proxy_pass http://127.0.0.1:3000/messages/`). **Link previews work in production. Suspicion
withdrawn.** Recorded rather than quietly dropped — and the container-vs-edge nginx distinction is
the reusable lesson: never conclude a routing question from the repo file alone.

### Production verification (owner-authorised read-only SSH, same session)

No deploy, no restart, no `.env` dump, no secret printed.

1. **BE-300 is NOT currently exposed.** `MEDIA_CLEANUP_GRACE_MS` is **absent** from
   `~/fireplace/.env` and unset in `fireplace-backend-1`, so `resolveGraceMs` takes the
   `DEFAULT_GRACE_MS` branch and the 15-minute window is live. The empty-string bug is real in
   code but not triggered. Latent landmine, not an incident — still worth the ten-line fix,
   because nothing warns when it trips.
2. **IP throttles are genuinely non-spoofable**, verified at the correct layer this time: all 11
   proxied host locations set `proxy_set_header X-Real-IP $remote_addr`, and nginx terminates TLS
   directly (`listen 443 ssl http2`, no CDN in front), so `$remote_addr` is the true client and
   overwrites any client-supplied value.
3. **NEW — BE-005 (LOW, class D real debt), `common/http-throttler.guard.ts:34-38`.** The
   tracker's `X-Forwarded-For` fallback reads the **first** hop via `split(',')[0]`, but nginx uses
   `$proxy_add_x_forwarded_for`, which **appends** — so the real client is the **last** element and
   the first is attacker-supplied. Dead code today only because `X-Real-IP` is set on every
   location and short-circuits the `??`. One forgotten nginx line from making every IP limit
   (including the register brute-force throttle) bypassable with a single header, with nothing
   failing loudly. Fix: drop the XFF fallback or read the last hop.
