# E2E cross-context ratchet repair

**Date:** 2026-07-23

## What was done
1. Investigated bob210 → bob208 message ids `17341`, `17342`, and `17174` against production rows, durable receiver diagnostics, sender key-bundle state, served frontend/backend metadata, and recent E2E/push/frontend diffs.
2. Ruled out the recent Contacts bundle and OTP-id patch. All three rows were type-2 whispers; diagnostics classified them as `duplicate`, not bad MAC, no-session, or identity reset. Sender identity/registration stayed stable.
3. Reproduced the missing failure class with real libsignal: two `EncryptionService` engines sharing one account but separate `_sessionTails` can roll back a shared ratchet or process one ciphertext twice. Pre-fix probe failed with `DuplicateMessageException old counter: 1, 0`.
4. Added an origin-wide, account+peer Web Locks layer around every web Signal session mutation. Unsupported browsers fail closed; Signal mutation never runs unlocked. Native retains the process-local queue.
5. Added exact-message-id + exact-ciphertext raw plaintext replay before the session lock releases. It covers duplicate delivery to another engine and app termination after Signal advances but before provider persistence. Retention is strictly capped at 40 under an account-wide prune lock; privacy cache clear removes it.
6. Bound provider decrypt calls to `messageId` and reloaded legacy `SharedPreferences` only on web before cross-engine reads, so another engine's structured plaintext is immediately visible without adding mobile I/O churn.
7. Bumped frontend `0.0.125` → `0.0.126`, updated the decryption runbook with the full incident record/correct production SQL, and added a source-controlled browser probe for same-name queuing plus missing-API fail-closed behavior.
