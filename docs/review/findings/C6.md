### C6-01 Client link-preview follows redirects with no per-hop SSRF re-check
- severity: High
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/services/link_preview_service.dart:36-52
- evidence: |
    static Future<Map<String, String?>?> fetchPreview(String text) async {
      final match = _urlRegex.firstMatch(text);
      ...
      // SSRF protection: skip private/local URLs
      if (_privateIpRegex.hasMatch(uri.host)) return null;
      try {
        final response = await http
            .get(uri, headers: {
              'User-Agent': 'Mozilla/5.0 (compatible; Fireplace/1.0)',
            })
            .timeout(const Duration(seconds: 5));
    The private-IP gate is applied ONLY to the originally-typed `uri.host`. The call uses the top-level
    `http.get`, whose `Request.followRedirects` defaults to `true` (max 5 hops); 3xx targets are chased
    automatically and are NEVER re-validated against `_privateIpRegex`.
- impact: Because link previews for E2E messages are generated CLIENT-side (the server can't read the
    plaintext — `messaging_provider.send.dart:838` calls `LinkPreviewService.fetchPreview(content)` on the
    SENDER), the server's hardened SSRF logic (`backend/CLAUDE.md:32`: `redirect:'manual'`, re-checks every
    hop) does NOT cover this path — the client is the sole gatekeeper and it skips redirect validation. A
    benign-looking public link (`https://short.url/x`) that 302-redirects to `http://127.0.0.1:8080/admin?...`,
    a LAN router page, or `http://169.254.169.254/…` will be fetched by the victim's device. On the **Android
    native build there is no CORS wall**, so the request actually reaches loopback/LAN/link-local hosts
    (blind SSRF / CSRF-to-LAN-GET / port-probe). Worse, the fetched page's `<title>`/`og:image` are then
    embedded into the outgoing E2E envelope (`return {'url':url,'title':title,'imageUrl':imageUrl}`), so an
    internal page's content can be exfiltrated to the conversation peer. On the iOS PWA, CORS blocks the
    cross-origin *read* but the request still fires.
- fix: Mirror the backend `fetchPreview` design — disable auto-follow (`http.Request(...)..followRedirects=false`),
    loop manually up to N hops, and re-run the private-host check on EVERY `Location` before re-issuing.
    Reference: `backend/src/chat/services/.../link-preview.service.ts` (`redirect:'manual'`, `isFetchableUrl`
    per hop) as documented in `backend/CLAUDE.md:32`.

### C6-02 Client private-IP filter is much narrower than the backend's
- severity: Medium
- confidence: High
- dimension: SECURITY (client)
- location: frontend/lib/services/link_preview_service.dart:11-14,45
- evidence: |
    static final _privateIpRegex = RegExp(
      r'^(localhost|127\.|10\.|172\.(1[6-9]|2\d|3[01])\.|192\.168\.|::1|fc00:|fd)',
      caseSensitive: false,
    );
    ...
    if (_privateIpRegex.hasMatch(uri.host)) return null;
- impact: The pattern does NOT block, and thus directly fetches: `169.254.0.0/16` link-local incl. the
    cloud-metadata IP `169.254.169.254` (the backend's `PRIVATE_IP_RE` explicitly blocks `169.254.x` per
    `backend/CLAUDE.md:50`); `0.0.0.0`; CGNAT `100.64.0.0/10`; IPv4-mapped IPv6 (`::ffff:127.0.0.1`); and
    alternate IPv4 encodings (`http://2130706433/` = 127.0.0.1, `http://0x7f000001/`, octal `0177.0.0.1`).
    Combined with C6-01 these give a direct (no-redirect-needed) SSRF to link-local/loopback from the
    client on native. `host.startsWith('[')`-style bracket stripping done in `isSafeImageUrl` (line 28) is
    also absent here, so bracketed IPv6 literals are matched inconsistently between the two checks.
- fix: Replace the prefix regex with structural parsing: resolve `uri.host`, reject by parsed-IP class
    (loopback, link-local, RFC-1918, CGNAT, ULA, mapped/compat IPv6, `0.0.0.0`) and normalize numeric host
    encodings before testing. Port the backend `PRIVATE_IP_RE` set so client and server agree. The
    DNS-resolves-to-private residual is already a KNOWN/ACCEPTED limit (`backend/CLAUDE.md:32`) — only the
    literal-IP and link-local gaps above are new.

### C6-04 AES-GCM runs on the calling isolate — docs claim an isolate that does not exist
- severity: Medium
- confidence: Medium
- dimension: PERFORMANCE
- location: frontend/lib/services/media_crypto_service.dart:21-50
- evidence: |
    Future<EncryptedMedia> encrypt(Uint8List bytes) async {
      if (bytes.length > maxBytes) { throw ArgumentError('File exceeds 20MB limit'); }
      ...
      final key = await AesGcmSecretKey.importRawKey(keyBytes);
      final ciphertext = await key.encryptBytes(bytes, iv);
    ...
    Future<Uint8List> decrypt(Uint8List ciphertext, String keyB64, String ivB64) async {
      ...
      final plaintext = await key.decryptBytes(ciphertext, iv);
    There is no `Isolate.run` / `compute` anywhere in the file; all work runs via `webcrypto` on the calling
    (UI) isolate. `frontend/CLAUDE.md:95` and `docs/review/FRONTEND-MODULE-MAP.md:35,71` both describe this as
    "AES-256-GCM **in isolate**".
- impact: On the Android native build, encrypting/decrypting media up to the 20 MB cap on the UI isolate can
    drop frames during send/playback (image/file/voice). On web, `webcrypto` delegates to SubtleCrypto so the
    work is already off the main thread, so this is native-only. The doc/code mismatch will also mislead future
    maintainers who assume key material is isolated off the main heap.
- fix: Either wrap `encryptBytes`/`decryptBytes` in `Isolate.run(...)` on native (note: webcrypto keys can't
    cross isolate boundaries, so pass the raw key bytes and import inside) for large payloads, OR correct the
    docs to say "AES-256-GCM via webcrypto on the calling isolate". Prefer fixing the docs at minimum.

### C6-05 `decrypt` has no internal size cap; key material kept in a non-zeroable String
- severity: Low
- confidence: High
- dimension: E2E / CLIENT CRYPTO
- location: frontend/lib/services/media_crypto_service.dart:6-16,40-50
- evidence: |
    class EncryptedMedia {
      final Uint8List ciphertext;
      final String keyBase64;   // key held as immutable String
      final String ivBase64;
    ...
    Future<Uint8List> decrypt(Uint8List ciphertext, String keyB64, String ivB64) async {
      final keyBytes = Uint8List.fromList(base64.decode(keyB64));
      ...
    `encrypt` enforces `maxBytes` (line 22) but `decrypt` does not; the 20 MB guard lives only at each call
    site (`playback_controller.dart:192,252`, `file_message_content.dart:49`, send paths). The fresh
    `keyBytes` (line 25) and the base64 key String are never wiped.
- impact: Any future caller that forgets the pre-check could decrypt an unbounded server blob into memory.
    One-shot media keys live in immutable Dart Strings (`keyBase64`) that cannot be zeroed and persist until
    GC — a minor defense-in-depth gap for an E2E app. Note the call-site guard checks the *ciphertext* length
    while `encrypt` caps the *plaintext* (ciphertext = plaintext + 16-byte GCM tag), a harmless off-by-tag
    inconsistency.
- fix: Add a `maxBytes` guard inside `decrypt` (defense in depth), and consider operating on `Uint8List`
    key material end-to-end so it can be zeroed after use rather than base64 Strings.

### C6-06 `GifService._fetch` shares one client; a concurrent call aborts the in-flight request
- severity: Low
- confidence: High
- dimension: RESILIENCE
- location: frontend/lib/services/gif_service.dart:32,53-64
- evidence: |
      http.Client? _client;
      ...
      _client?.close();
      _client = http.Client();
      ...

- impact: `fetchTrending` and `search` (and rapid paginated `offset` calls) share `_client`. If call B starts
    while call A's `await _client!.get` is in flight, B's `_client?.close()` closes A's client → A throws

    one long-lived client for the service lifetime and only close it in `dispose()`.

## Chunk summary
Media crypto core (AES-256-GCM, fresh key+IV per blob, no key logging) and blob/coordinator lifecycles are
sound. The ship-relevant gap is the **client-side link-preview SSRF**: it follows redirects without per-hop
revalidation (C6-01, High) and its private-IP filter misses link-local/alt-encodings (C6-02), so on the
no-CORS Android native build it can reach loopback/LAN/link-local hosts and leak internal page metadata into
the E2E envelope. Secondary: AES-GCM on the UI isolate vs docs (C6-04), native "download" lands in
inaccessible app storage (C6-07), and dead `audio_blob_url`/`audio_mime` code with contradictory docs (C6-09).
